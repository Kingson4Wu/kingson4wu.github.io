用户说：“帮我约 Leo 下周三开个会，大概半小时。”模型准确提取了已有信息，回复“下周三，与 Leo 开会，时长 30 分钟”，但日历接口需要 JSON，这句话不能直接传进去。

换成严格结构化输出，程序终于收到合法参数，`duration_minutes` 却变成了 `180`。接口照常执行，半小时的会被排成了三小时。

这个例子暂时只看时长；真正创建会议还需要确认具体时间。它点出了接入大模型时真正需要回答的问题：**要求模型按固定格式输出，会不会让它更容易把事情答错？如果会，格式稳定带来的收益，能不能抵消内容质量的损失？**

格式约束会影响生成过程，但质量不一定下降。简单抽取可能既更稳又更准，复杂推理、小模型或设计不合理的 Schema 则可能付出明显代价。给人看的回答，先看内容；交给程序的结果，内容正确和接口可用都得满足。真正要优化的是“这件事最后有没有做对”，不能只看 JSON 通过率。

## 一、为什么格式可能影响答案

最容易产生的误解是：模型先在内部想好一个完整答案，最后把它包装成 JSON。如果只是换个包装，当然不该影响内容。

但对直接生成答案的自回归模型来说，可见输出是逐 token 产生的。先写下什么，会成为后续生成的上下文。要求它从第一个字符就输出固定结构，等于改变了它抵达答案的路径。带独立推理阶段的模型可能在输出前做额外计算，所以“最终只返回 JSON”也不等于“模型没有推理”；需要区分具体模型的生成流程。

以日历任务为例，模型原本可能先写“下周三需要按用户时区换算……”，再确定日期。一个只准输出最终参数的 Schema 不允许出现这段可见说明。它仍可能得到正确日期，但我们不能假定：删掉了这一条生成路径，能力完全不受影响。

这里的 Schema，就是声明输出有哪些字段、各是什么类型、允许哪些值的规则。还要把两种限制分开。

**提示词要求格式，是让模型自己遵守。** 写“只返回 JSON”，模型仍有机会输出解释、Markdown 代码围栏或漏字段。这属于软约束。

**约束解码，是在选 token 时直接挡住不合法的候选。** 模型算出下一步的候选分数，约束引擎检查哪些候选接在当前前缀后，还能完成一个合法结果。其余候选被屏蔽，再从剩下的候选里选择。这不是等答案写完再修几个逗号。[OpenAI 的实现说明](https://openai.com/index/introducing-structured-outputs-in-the-api/)介绍的就是这种逐步限制采样的方式。

  <figcaption>筛选能判断“还能不能写成合法结构”，不能判断“这个会议到底应该持续多久”。</figcaption>
</figure>

比如下一步 A、B、C 的概率原本是 60%、25%、15%。A 不合法，被排除后，B 和 C 的概率变成 62.5% 和 37.5%。约束没有让模型重新学习这个任务，只是改变了当前能选什么。

若前缀是 \(h\)，允许的 token 集合是 \(A(h)\)，这个过程可以写成：

$$
P_{\mathrm{constraint}}(v\mid h)=
\frac{P_{\mathrm{model}}(v\mid h)\mathbf{1}[v\in A(h)]}
{\sum_{u\in A(h)}P_{\mathrm{model}}(u\mid h)}
$$

公式要说明的只有一点：**剩下的合法候选会被重新分配概率，但合法不代表正确。** 这一步也没有在所有合法完整答案中搜索最优解。它选出的 token 会继续影响下一步，因此局部筛选可能把生成带到一条格式正确、内容错误的路径上。

Temperature、Top-K、Top-P 改变的是采样范围和随机性，本身不检查 Schema。把 Temperature 调成 0，也不能替代结构约束或事实核对。

## 二、什么时候更稳，什么时候更容易答错

如果原文写“Tom，25 岁”，任务只是提取姓名和年龄，那么限制输出键名、整数类型和括号，主要是在排除接口噪声。正确答案本来就能放进这个结构，约束与任务方向一致。

但模型也可能返回：

```json
{"name": "Tom", "age": 35}
```

这份结果可以通过语法和字段类型检查，但年龄仍然错了。[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs)也明确保留了内容出错的可能。Schema 能规定年龄是整数，无法凭这个条件核对原文。

更麻烦的是，Schema 有时把正确答案挡在外面。原文只说“Tom 是成年人”，却强制 `age` 必须是整数，而且没有未知状态。模型即使意识到证据不足，也没法用这个接口准确表达它。此时提高格式通过率，可能只是让模型更稳定地填一个没有依据的数字。

类似问题还有：要求单选，实际有多个原因；只准输出“是”或“否”，实际需要补充条件；必须生成工具参数，实际应该先向用户确认时间。这些限制已经涉及答案能表达什么，不只是标点和字段类型。

设计 Schema 时，先检查三件事：正确答案能否放进 Schema？证据不足时能否返回 `null`、未知或待确认？字段描述有没有说明单位、时区和来源？“必须有这个字段”与“必须编一个值”不应混为一谈。

另外，解码器拿到了 Schema，不等于模型理解了字段。[llama.cpp 的文档](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)明确说明，普通 JSON Schema 约束不会自动注入提示词，工具调用另有处理方式。只限制 `duration_minutes` 是整数，却没说明它表示分钟，限制再严格也不能补上任务说明。

这些是从机制得到的风险判断，不能直接变成“所有格式约束都会降低质量”。模型是否熟悉这种格式、任务是否需要复杂推理、Schema 是否留有表达空间，都要用实验确认。

## 三、公开实验到底支持什么结论

现有证据同时包含提升和退化。不能挑一组数字，就给所有模型下结论。

[JSONSchemaBench](https://arxiv.org/html/2501.10868v3)用 Llama-3.1-8B-Instruct 比较了几种约束实现。三个任务分别是拼接单词末字母、跟踪物品交换后的归属、解答数学应用题，表中数字是任务准确率：

| 方法 | Last Letters | GSM8K | Shuffle Objects |
| --- | ---: | ---: | ---: |
| 无约束 | 50.7% | 80.1% | 52.6% |
| Guidance | 54.0% | 83.8% | 55.9% |
| Outlines | 53.3% | 81.6% | 53.0% |
| llama.cpp | 52.0% | 82.4% | 52.6% |
| XGrammar | 51.2% | 83.7% | 52.7% |

这里没有出现准确率下降。不过，它使用的结构包含 `reasoning` 和 `answer` 两个字段，给可见推理留了位置。论文也把 Guidance 的部分提升解释为可能与 token healing（处理提示词末尾与生成内容之间的分词边界）有关。不能把所有差异都归于“加了格式约束”。

另一项针对小模型的预印本 [The Constraint Tax](https://arxiv.org/abs/2605.26128)中，硬约束把 Schema 有效率从 61.5% 提到 100%，答案准确率却从 19.7% 降到 11.0%。这里的硬约束方案只允许输出答案。把内容正确与格式合法一起计算，可执行准确率其实是从 12.0% 降到 11.0%，这也说明分母和指标不能混着看。

该研究的日历任务更直观：Qwen2.5-1.5B 的提示词 JSON 与硬工具 Schema 都是 100% 结构合法，可执行准确率却分别是 91.5% 和 48.0%。格式已经没有提升空间，内容退化就直接成了损失。这些数字只适用于论文测试的小模型和任务，不能拿来估计 GPT 或 Claude 的固定损失。

两项实验的模型、任务、Schema 和实现并不相同，尤其不能忽略“允许推理字段”和“只准最终答案”的区别。它们支持的判断是：**格式与内容必须分别测；具体有没有损失，要在具体设置下比较。** 它们没有给出一个所有模型通用的“约束税”。

[Draft-Conditioned Constrained Decoding](https://proceedings.mlr.press/v306/reddy26a.html)研究了先生成自由草稿，再参考草稿做约束生成的方法，在所测结构化推理任务中取得提升。这个结果支持把分阶段方案作为候选，但多一次生成意味着更多延迟和成本，草稿本身也可能错。

## 四、现在的接口能保证到哪一步

截至 2026 年 10 月核对的文档，OpenAI 和 Anthropic 都提供严格结构化输出，开源部署也有 llama.cpp、XGrammar、Guidance、Outlines 等实现。使用前先分清三种能力：

| 方式 | 主要解决什么 | 没有解决什么 |
| --- | --- | --- |
| 提示词要求 JSON | 提高格式遵循率 | 无法从机制上排除格式错误 |
| JSON mode | 输出可解析的 JSON | 未必符合指定字段和类型 |
| 严格 Schema 输出 | 约束受支持的字段、类型等 | 不证明字段内容符合事实 |

OpenAI 发布 Structured Outputs 时，报告特定 GPT-4o 模型在复杂 Schema 基准中的符合率为 93%，加入确定性约束后达到 100%。这是 [Schema 符合率评测](https://openai.com/index/introducing-structured-outputs-in-the-api/)，不是会议时间正确率，也不是复杂问答准确率。模型经过格式相关训练和推理时加硬约束是两种作用，不能混成一个指标。

写了 Schema，也要确认服务商实际支持哪些约束。[OpenAI strict 模式](https://developers.openai.com/api/docs/guides/structured-outputs)要求字段列入 `required`、对象使用 `additionalProperties: false`；可无确定值的字段可以允许 `null`。[Anthropic SDK helper](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)会把部分不支持的数值或长度限制移到描述中，再由支持校验的 helper 按原 Schema 检查。写在描述里的要求，不能当作生成时已经被硬性执行。

这里还要区分三种情况：约束根本没写进去、实现不支持这个约束、约束无法判断事实。例如“年龄不得超过 120”可以用 [JSON Schema 的数值范围](https://json-schema.org/understanding-json-schema/reference/numeric)表达，但服务商未必支持；“年龄是否等于原文中的值”则需要核对来源。llama.cpp 的[文档](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)还提醒，某些不支持的关键字可能被静默跳过，接口接受了 Schema 不等于每条规则都已生效。

约束引擎本身也需要测试。[JSONSchemaBench 的覆盖率实验](https://arxiv.org/html/2501.10868v3)发现过编译失败、错误排除合法结果、放过不合法结果三类问题。选引擎时，既要测它能处理多少业务 Schema，也要用独立校验器检查输出，不能只在编译成功的样本中计算通过率。

接口拒答、达到 token 上限或中途断开，也不能按正常完整对象处理。流式输出尤其要注意：途中收到的只是参数片段。[Anthropic 的工具参数流说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)要求客户端处理不完整参数；有副作用的工具应等参数完整并通过校验后再执行。

即使响应正常完成，也不要省掉独立检查。Anthropic 的[已知限制](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)提到，字符串枚举可能出现大小写不一致而没有特殊停止原因。业务若要求精确枚举值，应校验并按预先约定的规则处理，不能把任意近似值直接传给下游。

## 五、质量重要，还是格式可用重要

给人看一段解释，内容正确、推理清楚最重要。没有下游接口需要 JSON，就没有必要为固定字段增加限制。

交给日历、订单或数据库接口时，格式是准入条件。程序无法读取的正确答案还需要转换；程序能读取的错误答案则应该被拦下。**接口边界要求结构可用，验收结果要求事情做对。** 不能因为结构通过了，就降低对内容的要求。

举个纯粹用于说明的数字例子。100 个请求，方案 A 有 90 个格式通过，其中 85 个任务正确；方案 B 的 100 个格式都通过，却只有 75 个任务正确。B 的 JSON 指标漂亮，实际完成的事更少。这三个数量要直接统计，不能把分别计算的格式通过率与内容准确率随手相乘，因为两种错误可能相关。

如果错误只导致多一次解析重试，代价通常可控；如果错误参数直接创建三小时会议或修改错误订单，损失就大得多。选择方案时应把错误执行、漏执行、转人工和重试的代价放进去，而不只是算平均成功率。

工具调用尤其如此。[strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)限制工具名和参数形状，不保证模型选对了工具或目标。比如 `search` 收到 `{"query":"订单 123"}`，参数结构没有问题，但也许用户问的是订单 132，甚至没有权限查看订单 123。

  <img src="/assets/zh/posts/20261002-structured-output-constrained-decoding/tool-call-validation-flow.svg" alt="模型生成工具参数后，应用检查语义、业务条件、权限，再执行并检查结果">
  <figcaption>完整且合法的参数只是进入校验的起点，不能直接当成执行批准。</figcaption>
</figure>

应用仍要检查对象、权限和业务前置条件，并核对执行结果。[OWASP 的 Agent 权限建议](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)也要求限制工具能力和权限。离线 eval 可以帮助选方案，不能替某一次请求做授权。

## 六、实际工程里怎么选

是否使用约束，应由应用的接口要求决定，不必让模型每次猜。先看输出交给谁，再看失败会造成什么后果：

| 场景 | 可以从什么方案开始 | 还需要检查什么 |
| --- | --- | --- |
| 给人看的解释、分析 | 自由文本 | 事实、遗漏和可读性 |
| 数据抽取、页面展示数据 | 直接严格结构化输出 | 完成状态、来源一致性、独立 Schema 校验 |
| 搜索、查询等只读工具 | 工具参数 Schema | 是否该调用、对象是否正确、读取权限 |
| 创建会议、修改订单等操作 | 严格参数结构，加执行前校验 | 授权、业务条件、重复执行和实际结果 |

### 格式稳定了，内容却变差怎么办

简单抽取可以先用直接严格输出。如果评测发现质量下降，或者接口不支持所需的约束，再比较下面三种处理方式。

**先调整 Schema。** 原本单选的原因改成数组，分类之外允许具体说明，证据不足时返回未知或 `null`。这适合错误来自表达空间不足的情况。不能为了提高通过率，把真正的业务限制删掉；如果会议时长必须在允许范围内，生成阶段不支持这个范围限制，也要在执行前检查。

**再比较分阶段生成。** 先形成语义结果，再转换成接口结构。如果第一阶段已经得到可信的字段值，优先用程序序列化，不必再让模型抄一遍；只有仍需解释或转换时，才考虑第二次模型生成。它适合直接约束影响复杂判断的情况，代价是额外步骤、延迟和可能的语义漂移。前一阶段答错，后一阶段不会因为格式严格就自动纠正。前面的[草稿辅助约束解码研究](https://proceedings.mlr.press/v306/reddy26a.html)支持测试这种思路，不能代替业务评测。

**也可以生成后校验，有限重试。** 先按提示生成 JSON，再解析和校验，失败时带上错误信息重新生成。这适合格式偶尔出错、可以容忍重试的任务。它没有单次成功保证，重试也不自动修正事实；要设置次数上限，记录最终失败率，并给失败请求明确的处理路径。

这三种方案分别改变接口表达、生成过程和失败处理，可以组合使用。选择仍要看最终正确处理了多少请求，以及为此多花了多少时间和费用。

重试还必须区分两件事：**重新生成尚未执行的参数，与重新执行已经发出的操作。** 前者可以重新询问模型；后者如果没有幂等键或去重，可能创建两个会议、重复修改订单。执行超时后，应先查询操作状态，再决定是否重试。

### 上线后，每次请求仍要走校验流程

离线 eval 是用来选方案的。上线后的检查负责判断当前这次请求能否继续：

1. 确认响应完成，检查拒答、截断和连接中断。
2. 解析完整结果，用独立校验器核对 Schema。
3. 检查字段与来源是否一致，单位、时区、目标对象是否正确；信息不足时进入确认流程。
4. 核对用户权限、业务前置条件和重复执行状态，再调用工具。
5. 检查实际执行结果，记录失败在哪一步、是否已经产生副作用。

这些步骤各有作用。格式错误应进入修复或失败处理，内容错误不能靠“再 parse 一次”解决，下游执行失败也不一定需要重新生成答案。把失败位置记清楚，后续才知道该改 Schema、模型，还是业务服务。

## 七、怎样做一份能回答问题的 eval

eval 要回答的是：同一个模型做同一批任务，加约束以后，到底少了哪些错，又多了哪些错？

先用同一批样本比较四种方案：提示词要求 JSON、JSON mode（接口支持时）、直接严格输出、先生成语义草稿再严格输出。自由文本可以作为理解能力的参考，评测时提取其中的答案；如果要把它当成生产方案，就必须连同转换和校验成本一起计算。

固定模型版本、后端、任务说明和采样参数。对于能开关约束的本地引擎，优先在相同提示词和相同目标结构下做对照，尽量隔离硬约束的影响。另做一组实用方案对比，允许优化 Schema 和提示词，但清楚记录变化。不要把“换了模型、加了示例、允许推理字段”的提升，全算到约束解码头上。

### 样本要包括模型应该停下来的时候

日历任务可以从下面这些样本开始，每条预先写好正确参数或应有状态：

| 输入情况 | 要验证的行为 |
| --- | --- |
| 明确日期、时间、参与人、时长 | 提取与单位换算正确 |
| “下周三下午”，但缺少具体时间 | 请求确认，不擅自填时间 |
| 多个时区或跨日 | 使用给定基准时间和用户时区 |
| “改成四十五分钟，其他不变” | 正确处理更正与已有上下文 |
| 用户只是在讨论安排方式 | 不创建会议 |
| 无权限修改某个日历 | 被授权检查拦截 |
| 截断、拒答、Schema 不支持 | 明确失败，不执行残缺参数 |

正常输入之外，缺失信息、歧义和“不该调用”的样本很关键。只有每条都能填写所有字段的样本，发现不了 Schema 强迫模型补全的风险。

### 至少把三个结果分开记

**格式通过率**：全部请求中，完成响应且通过独立 Schema 校验的比例。编译失败、拒答和截断单独记原因，不从总请求里悄悄删除。

**内容正确率**：全部请求中，语义答案正确的比例。格式错误但内容正确的结果可以由固定提取规则或人工复核识别；无法判断的单独标记。它用于观察模型理解是否退化，不代表该输出能直接执行。

**端到端成功率**：全部请求中，同时满足结构、内容和业务要求，得到预期结果的比例。该确认时进入确认流程、该拒绝时正确拒绝，也可以是成功；不是必须执行一个工具才算成功。日历调用用沙箱或模拟接口验证，不在真实日历上试错。

对参数抽取，用参考值检查日期、时长、参与人；需要解释质量时，预先约定事实、遗漏、条件表达等评分标准。LLM judge 可以辅助筛查，不能因为另一模型觉得“看起来对”，就替代确定字段的核验。

### 最有价值的是翻出那些“合法但错了”的样本

把同一条输入在各方案下的输出并排看。自由方案正确、严格方案错误，才是需要重点排查的退化；反过来的样本则显示约束解决了什么。先看差异样本，比先看一张总分表更容易找到原因。

如果错误集中在缺少信息，先改 Schema 的未知状态；如果集中在需要计算或多步判断的任务，比较保留必要推理空间或分阶段方案；如果内容正确只是结构偶尔坏掉，再比较严格输出与有限重试。分阶段封装也要核对前后语义一致，不能让包装步骤把 30 改成 180。

同时记录总延迟、P95（95% 的请求延迟不超过这个值）、token 消耗、重试次数和最终失败率。冷启动与缓存命中分开统计，Schema 编译失败也算成本。如果还要选约束引擎，可以像 [JSONSchemaBench](https://arxiv.org/html/2501.10868v3) 那样拆开编译时间、首 token 时间和每 token 时间；业务方案仍要比较包括重试和额外调用在内的总耗时。采样设置允许时重复运行；即使 Temperature 为 0，也保留多次运行结果，别拿一次偶然差异当稳定结论。小样本应给出不确定范围，优先采用按输入配对的比较。

简单抽取可以先用直接严格输出，再用这份 eval 检查效果。如果它已经既准又稳，就不用额外拆两次调用；如果它只让错误答案更容易被接口接受，就该调整生成方式或模型。

格式是为了让正确结果进入程序。选方案时，要看在可接受的成本下，有多少请求被正确处理，以及那些没处理对的请求，能不能在执行前被发现。
