假设要从一段文字中提取姓名和年龄，程序希望收到的是 `{"name":"张三","age":28}`。在提示词里写“只返回 JSON，不要解释”，模型多数时候能照做，但偶尔会加一句说明、漏掉字段，或者把年龄写成字符串。人读起来没什么障碍，程序解析或校验时却可能出错。

程序要稳定读取模型输出，就得限制它生成的格式。即使格式稳定了，接入工具和业务操作时，还要继续判断内容与执行结果是否正确。

## 一、从提示词到严格结构化输出

只在提示词里要求“按这个格式回答”，属于软约束。模型可能遵守，也可能偏离。把提示写得更详细、加几个示例，通常能提高遵循率，但不能从机制上排除多余文字、错误字段或无效 JSON。

如果使用支持 JSON mode 的接口，可以要求结果是可解析的 JSON。但“是 JSON”和“符合指定的字段结构”仍是两回事。OpenAI 的[结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs)就明确区分了两者：`{"age":"28"}` 是合法 JSON，却不满足年龄必须为整数的要求。

需要固定字段、类型或枚举值时，可以使用服务商支持的严格结构化输出，并提供 Schema。约束引擎会在生成过程中排除违反已生效约束的候选。它解决了“模型能否按接口形状返回”的问题；至于提取出的年龄是不是原文中的年龄，还要另外判断。

严格结构化输出直接作用于生成过程。要理解这种限制如何生效，需要先看模型怎样逐 token 生成文本。

## 二、约束解码怎样工作

自回归模型每一步都根据已有上下文，计算下一个 token 的概率分布：

$$
P(x_{t+1}\mid x_1,\ldots,x_t)
$$

Transformer 架构中的解码器（Decoder）计算表示和 logits，即各候选 token 的原始分数；解码策略（decoding strategy）再决定如何选择。选中的 token 加入上下文，模型继续计算下一步。常见的选择方式和采样设置有：

| 方式或设置 | 每一步怎样处理候选 | 主要影响 |
| --- | --- | --- |
| Greedy | 直接选当前分数最高的 token | 较稳定，但只做局部选择 |
| Temperature | 采样前调整概率分布的尖锐程度 | 改变随机性与多样性 |
| Top-K | 只在分数最高的 K 个 token 中采样 | 排除低排名候选 |
| Top-P | 只在累计概率达到阈值的最小候选集中采样 | 候选集大小随分布变化 |

Temperature、Top-K 和 Top-P 通常是采样时使用的设置；它们本身并不判断输出是否符合 Schema。

约束解码在“模型给出候选”和“选出 token”之间增加一道限制。典型实现会把 Schema、正则表达式或语法规则编译为可随输出前缀推进的状态；每一步根据当前状态找出允许的 token，屏蔽其余候选，再按原来的解码策略选择：

  <figcaption>蓝色步骤表示约束引擎的筛选；模型仍负责给出候选分数，解码策略仍负责选择。</figcaption>
</figure>

这里判断的不是“单个 token 是不是合法 JSON”，而是把它接到现有前缀后，是否仍有可能完成一个合法结果。一个 JSON 键可能拆成多个 token；嵌套对象也需要持续跟踪语法状态。简单格式可以用有限状态机制处理，嵌套和递归结构则需要能跟踪语法层级的实现。OpenAI [介绍约束采样实现时](https://openai.com/index/introducing-structured-outputs-in-the-api/)讲的正是这种逐步筛选候选的过程，通常无需先生成完整答案、发现错误后再回滚修复。

约束会改变下一步的概率。假设 A、B、C 原本分别占 60%、25%、15%，但 A 不合法；屏蔽 A 并重新归一化后，这一步 B 和 C 的概率变成 62.5% 和 37.5%。写成公式，若前缀是 \(h\)，允许的 token 集合是 \(A(h)\)，则：

$$
P_{\mathrm{constraint}}(v\mid h)=
\frac{P_{\mathrm{model}}(v\mid h)\mathbf{1}[v\in A(h)]}
{\sum_{u\in A(h)}P_{\mathrm{model}}(u\mid h)}
$$

这是**当前一步**的条件分布，不是在所有合法完整答案里寻找全局最优。即使用 Greedy 每步都选概率最高的合法 token，最后得到的序列也未必是概率最高的合法序列。限制还会影响后续生成轨迹，但不能仅凭这一点断定语义质量一定上升或下降。

解码器**使用** Schema，不代表模型**看见** Schema。以 [llama.cpp 的普通 JSON Schema 约束](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)为例，Schema 只用于限制输出，不会自动写入提示词；工具调用又有不同的处理方式。因此，字段的业务含义仍需要在任务说明中说清楚。

## 三、格式正确离答案正确还有多远

假设原文写的是“Tom，25 岁”，模型返回：

```json
{"name": "Tom", "age": 35}
```

这份结果可以通过语法和字段类型检查，但年龄仍然错了。反过来，如果规则只是“年龄不得超过 120”，[JSON Schema 的数值范围关键字](https://json-schema.org/understanding-json-schema/reference/numeric)可以表达它，但具体服务商的严格输出模式未必支持这些关键字。关键是分清**约束没有写进去**、**当前实现不支持该约束**，以及**约束本身无法判断事实**这三种情况。

接入程序时，需要分别检查以下几层：

| 层次 | 主要问题 | 谁来核对 |
| --- | --- | --- |
| 语法 | 结果能否解析成 JSON？ | 解析器 |
| Schema | 字段、类型、枚举等是否满足实际生效的约束？ | 独立的 Schema 校验器 |
| 事实与语义 | 提取或回答是否符合输入证据？ | 来源核对、领域校验 |
| 业务规则 | 状态、金额、时序等是否允许？ | 业务服务 |
| 权限与执行 | 当前用户能否操作，操作是否真正成功？ | 授权系统、工具执行结果 |

Schema 还得允许模型表达“不知道”。输入没有年龄，却强制 `age` 是整数，模型就可能填一个看似合理的数字。可以允许 `null`，或用状态字段区分“有答案”和“证据不足”。OpenAI 的[文档](https://developers.openai.com/api/docs/guides/structured-outputs)也提醒，当输入与 Schema 不相干时，模型可能仍试图把结构填满。

写了 Schema，也要确认服务商实际支持哪些约束。以 [OpenAI strict 模式的规则](https://developers.openai.com/api/docs/guides/structured-outputs)为例，对象需要 `additionalProperties: false`，字段都需列入 `required`；若字段可以没有确定值，可以用包含 `null` 的类型表示。Anthropic 的 [SDK helper 说明](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)指出，部分不受支持的范围约束可能被移到字段描述里，再由 helper 按原 Schema 校验响应。llama.cpp 的 [Grammar 文档](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)则提醒，某些不受支持的关键字可能被静默跳过。不能只看 Schema 文件写了什么，还要测试约束是否真正生效，并独立校验最终结果。

问题还可能出在约束引擎本身。[JSONSchemaBench 的覆盖率测试](https://arxiv.org/html/2501.10868v3)观察到三类失效：Schema 编译失败、把本来合法的结果挡掉，以及没有拦住不合法的结果。因此评测要同时看 Schema 的可用范围和最终结果的独立校验通过率，不能只统计成功生成的样本。

严格结构化输出还要看响应是否正常完成。[OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs) 和 [Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) 都提醒，拒答、达到 token 上限或中途断开时，不能假设拿到的仍是符合 Schema 的完整对象。流式输出尤其如此：途中收到的只是片段。[Anthropic 对工具参数流的说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)指出，客户端需要处理不完整的参数；有副作用的工具应等参数完整并通过校验后再执行。

即使响应正常完成，也不能把服务商的“严格”当作无需校验的承诺。Anthropic 的[已知限制](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)提到，字符串枚举值的大小写可能与 Schema 不一致，而且不会产生特殊的停止原因。对大小写敏感的业务值，仍要独立验证。

## 四、工具调用把问题推到了执行层

返回 JSON 是把结果交给程序读；工具调用则可能让程序接着搜索、发消息或修改订单。模型需要决定**是否调用、调用哪个工具、传什么参数**。以 Anthropic 的 [strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use) 为例，工具名被限定在可用工具内，参数按相应 Schema 的受支持部分约束；但这不能保证此时应该调用工具，也不能保证从多个可用工具中选对了一个。最终回复的 JSON 格式和工具调用的严格约束是两个接口，可以同时使用。

比如 `search` 工具要求 `query` 是字符串。模型传入 `{"query":"订单 123"}`，参数结构没有问题，但也许用户问的是订单 132，甚至没有权限查看订单 123。把参数限制为字符串，解决不了对象选错或越权读取。

图中分开的是逻辑步骤，工具选择和参数生成可能发生在同一次模型生成中。约束可以在生成参数的每一步生效；应用则要等参数完整后，核对目标、业务条件和权限，再决定是否执行。

尤其是会修改状态的工具，结构合法的字符串仍可能是危险命令、受提示注入影响的 URL，或用户无权访问的资源标识。工具应以最小权限运行，并对高影响操作增加执行控制；这也是 [OWASP 对 Agent 权限](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)的建议。

## 五、格式更稳，会不会让答案变差

硬约束排除多余逗号、非法字段时，可能提高可用性；如果 Schema 只允许从 A、B、C 中选一个原因，任务却需要多个原因、置信程度或证据，它也可能压掉有用信息。两种效果都可能发生，不能从“候选被屏蔽”直接推出统一的质量结论。

公开实验给出的结果并不一致。[JSONSchemaBench](https://arxiv.org/html/2501.10868v3)用 Llama-3.1-8B-Instruct 比较了几种约束实现，在其三个任务上的准确率如下：

| 方法 | Last Letters | GSM8K | Shuffle Objects |
| --- | ---: | ---: | ---: |
| 无约束 | 50.7% | 80.1% | 52.6% |
| Guidance | 54.0% | 83.8% | 55.9% |
| Outlines | 53.3% | 81.6% | 53.0% |
| llama.cpp | 52.0% | 82.4% | 52.6% |
| XGrammar | 51.2% | 83.7% | 52.7% |

在这组条件下，约束没有降低准确率。论文认为 Guidance 的部分提升**可能**与 token healing 有关，因此不能把差异全部算作约束本身的效果。

针对较小模型的预印本 [The Constraint Tax](https://arxiv.org/abs/2605.26128) 得到了相反的结果：在其测试设置中，硬约束把 Schema 有效率从 61.5% 提到 100%，答案准确率却从 19.7% 降到 11.0%；结构合法但答案错误的比例从 49.5% 升到 88.9%。

这项研究的日历工具调用任务中，Qwen2.5-1.5B 的提示词 JSON 和硬工具 Schema 都达到 100% 结构合法，可执行结果准确率却分别是 91.5% 和 48.0%。这些数字来自特定小模型和任务，不能外推成所有模型的固定损失；它们说明的是格式合格率与任务正确率必须分开测。

一种可能的改法，是先让模型形成语义草稿，再结合草稿生成受约束的结构。[2026 年的一项 ICML 研究](https://proceedings.mlr.press/v306/reddy26a.html)在部分结构化推理任务中观察到这种方法优于直接约束输出。但它多了一次生成，不应未经评测就当成默认方案。

商业模型的公开数字也要看清指标。[OpenAI 发布 Structured Outputs 时的评测](https://openai.com/index/introducing-structured-outputs-in-the-api/)称，GPT-4o-2024-08-06 经过针对复杂 Schema 的训练后，在其基准中的符合率为 93%；加入确定性约束解码后，报告的符合率达到 100%。同一资料还列出 GPT-4-0613 低于 40%，但它与 GPT-4o 是不同模型，不能把二者差异全归因于约束解码。这些数字衡量的是 **Schema 符合率**，不是提取事实、选对工具或完成任务的准确率；也不足以算出 GPT 或 Claude 在各类业务任务中的统一“约束税”。

## 六、把约束放进实际工程

### 先按接口和失败代价选方案

是否使用约束，应由应用的接口契约决定，不必让模型每次运行时猜测。不同场景对输出格式和后续检查的要求并不相同：

| 场景 | 可采用的输出方式 | 还要检查什么 |
| --- | --- | --- |
| 普通解释 | 自由文本 | 事实与可读性 |
| 数据抽取、UI 数据 | 受支持的严格结构化输出 | 完成状态、来源一致性、独立校验 |
| 查询工具 | 工具参数 Schema | 是否该调用、参数指向的对象、读取权限 |
| 修改订单等有副作用的工具 | 严格参数结构与下游执行控制 | 授权、业务前置条件、执行结果 |

简单抽取任务可以先试直接严格输出。如果格式稳定了，答案却变差，或者需要的 Schema 约束无法在生成时生效，还有三种值得比较的处理方式：

1. **调整 Schema。** 过窄的 `reason` 枚举可以改成“分类 + 具体说明”，需要多个原因时用数组表达，证据不足时允许“未知”或 `null`。这能给模型保留必要的表达空间，但不能为了提高通过率而删除真正的业务限制。
2. **分阶段生成。** 先形成语义结果，再根据它生成符合接口的结构。前一阶段可以少受格式限制，后一阶段负责封装；代价是额外的生成步骤、延迟和 token，且第一阶段的事实错误不会自动消失。[草稿辅助约束解码的研究](https://proceedings.mlr.press/v306/reddy26a.html)提供了这种思路的实验结果，不能据此断定所有任务都适合分阶段。
3. **自由生成后校验与有限重试。** 先生成，再解析、按 Schema 校验，不合格时有限次数重试。这适合能容忍偶发失败、也不值得为格式引入硬约束的场景；它没有单次成功保证，重试也不会自动纠正事实错误。重试成本和最终失败率要一起统计。有副作用的工具还要区分重新生成参数与重试已执行的操作，后者需要幂等或去重保障。

这三种方法分别改变接口表达、生成过程和失败处理，不存在固定的优先顺序。选择要看同一任务上的最终成功率与成本，而不是只比较 JSON 能否解析。

### 把质量和成本一起评测

约束引擎可能有语法编译和逐 token 检查成本，但总延迟还受缓存、输出长度、失败重试和额外调用影响。[JSONSchemaBench 的效率评测](https://arxiv.org/html/2501.10868v3)分别统计编译时间、首 token 时间和每 token 时间；如果只在引擎能处理的 Schema 上测速，还会漏掉编译失败带来的覆盖率问题。Temperature 设为 0 也不能保证跨模型版本、推理后端和计算环境得到相同输出。[OpenAI 的可复现性说明](https://developers.openai.com/api/docs/guides/advanced-usage)同样建议记录影响输出的参数与后端信息。

比较自由生成、JSON mode、直接严格输出和分阶段方案时，应固定模型版本、任务样本、提示词、Schema、后端和解码参数。测试样本除了常规输入，还应覆盖缺少答案、输入与任务无关、不应调用工具、复杂结构、响应截断和高影响操作。至少分开记录：

- **结构结果**：Schema 编译成功率、独立校验通过率，以及拒答和截断如何计入。
- **任务结果**：事实准确率、工具选择和参数准确率、业务有效率、最终任务成功率。
- **运行成本**：首次与缓存命中延迟、首 token 时间、总延迟、输出 token、重试率和成本。

### 上线后逐次校验

离线评测用来选择模型、Schema 和生成方式；线上校验用来拦截当前请求中的错误和越权。前者提供统计判断，不能替后者批准某一次工具调用。接到响应后，处理顺序应当明确：

1. 确认响应已经完成，检查拒答和截断状态。
2. 解析完整结果，用独立校验器检查实际返回的结构。
3. 核对内容来源、业务前置条件和当前用户权限。
4. 执行必要操作，并检查工具或下游服务的实际结果。
5. 记录失败发生在哪一步，以及是否已经产生副作用，供后续评测改进。

这套检查能区分“格式通过但事实错误”和“参数合法但执行失败”。如果只记录一个总成功率，排查时很难知道应该改 Schema、改生成方式，还是改下游执行逻辑。

## 小结

约束解码能把“尽量按格式输出”变成对生成过程的限制，让机器接口更稳定。但它只解决了链条中的一部分：一个通过 Schema 的值，仍可能与原文不符；一份合法的工具参数，也可能对应错误或越权的操作。

评估这类接口时，结构合格率、内容正确率和任务完成率要分开看。只统计一个笼统的“成功率”，结构越稳定，越可能掩盖内容和执行层面的错误。
