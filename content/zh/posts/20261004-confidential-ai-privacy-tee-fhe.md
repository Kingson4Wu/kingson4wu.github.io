企业使用大模型，可以自己部署，也可以调用第三方服务。自己部署能掌握更多环节，但要承担算力和维护成本；第三方服务更方便，却要回答一个问题：**交出去的数据，谁有能力读取？**

Confidential AI（机密 AI）关注的是数据参与计算时的保密。常见路线是可信执行环境（Trusted Execution Environment，TEE）：模型在硬件隔离的环境中处理明文，限制外部访问。完全同态加密（Fully Homomorphic Encryption，FHE）则让服务端直接计算密文，连推理软件也不必拿到原文。

第三方模型通常通过应用程序接口（Application Programming Interface，API）接受请求。图中的远程证明（Remote Attestation，RA）用于在交出数据前核对远端环境；安全多方计算（Secure Multi-Party Computation，MPC）则让多方按协议共同计算，保护各自的私有数据。

## 普通模型 API：传输加密，服务端仍能读

### HTTPS 和隐私条款，保护的是不同环节

HTTPS 用于网页和 API 的加密通信。在正确验证对端身份的前提下，它保护连接两端之间的传输，防止途中被窃听或篡改。普通模型 API 收到请求后，通常要解开内容，才能分词、检索和推理。即使不保存到磁盘，程序也可能在内存中读取明文。

“不用于训练”约束用途，“零保留”约束保存，客户管理密钥增强存储与密钥控制。这些措施都有价值，但如果服务端有解密权限，就仍能在计算时读取内容。

**关键是在哪里解密、谁能读取。没有保存或训练，不等于没有看到。**

### 向量不是密文

Token（词元）是模型处理文字的基本单位，可以是一个字、词或词的一部分。模型把文字转换成 token 编号，再转换成向量，也就是一组用于计算的数值。编号通常可以用对应分词器恢复文本表示，向量也保留内容信息，可能用于关联和推断。

**把明文转换成向量，不等于把数据加密。** 模型“解码”是在选择 token，密码学“解密”才是在用密钥恢复明文。

选方案时，还要区分保护对象：用户输入、检索文档、输出和模型权重，可能属于不同主体。信任推理软件、只防范云管理员，与连推理软件也不能读，是两种要求。

## TEE：硬件隔离数据，客户验证运行环境

### 保护环境里的软件，仍然处理明文

TEE 利用安全硬件建立隔离环境。获准软件在里面处理明文，宿主机和云管理员等外部主体，在平台声明的安全范围内受到访问限制。

  <img src="/assets/zh/posts/20261004-confidential-ai-privacy-tee-fhe/tee-data-boundary.svg" alt="TEE 限制边界外访问；获准的软件仍在保护环境内处理明文。" width="480" height="686">
  <figcaption>TEE 保护的是执行边界；边界内的软件仍有读取数据的能力。</figcaption>
</figure>

大模型常用图形处理器（Graphics Processing Unit，GPU）加速计算。保护也要覆盖 GPU 和相关通信通道；只保护中央处理器（Central Processing Unit，CPU），不能保证整条推理路径安全。

硬件隔离也不会自动阻止内部软件记录或外发数据。操作系统、驱动、推理程序和数据出口，仍需要按保护范围审查。

**TEE 的核心是限制环境外的读取；环境内的软件仍须可信。**

### 软件指纹为什么不能随便伪造

这里使用的密码学 Hash（哈希值）可以理解为内容的数字指纹，用来检查软件或配置是否与批准对象一致。远程证明提供签名证据，让客户核对这些指纹及平台状态。关键在于：**实际加载内容的测量值，由硬件支持的可信机制产生和保护，再由受保护的证明密钥签名。**

以启动测量为例：批准启动 A，实际启动 B，只要两者的差异属于测量范围，报告中的测量值就会不同。知道 A 的公开 hash，也不能拿它替换受保护的测量记录；修改签名后的报告，会使验证失败。这个保证以硬件、固件和密码机制未被攻破为前提。

报告还可能包含软件自行提交的信息，不能把这些字段当成实际测量。“被硬件签名”不等于“被硬件测量”。启动测量不等于每次请求都检查全部运行代码；后来加载的模型、插件和配置，需要获准程序继续校验并维护完整性。

**防伪靠的是受保护的测量与签名机制，hash 本身可以公开。**

### 硬件身份靠证书链，连接对象也要核对

客户通过**证明密钥的证书链**确认报告来源。证书链是一串逐级签发的身份证明：客户从预先信任的硬件厂商根证书出发，确认用于验证报告的公钥属于获认可的证明机制。它与 HTTPS 的认证思路相似，这里认证的是硬件证明密钥。

<figure>
  <img src="/assets/zh/posts/20261004-confidential-ai-privacy-tee-fhe/attestation-certificate-chain.svg" alt="客户预先信任 AMD 根证书，依次验证中间证书与证明密钥证书，再验证报告签名。" width="480" height="544">
  <figcaption>以 AMD 的一条证明路径为例：证书链确认签名来源，测量值确认被证明的环境。</figcaption>
</figure>

公钥用于验证签名，私钥用于生成签名。证书和公钥可以公开复制，但复制者拿不到受保护的签名私钥，无法据此伪造报告。客户还要检查平台版本、证书状态和保护配置。

验证来源只是第一步。还要确认报告足够新，并把证明绑定到实际通信端点，避免拿另一台安全机器的报告来冒充。**数据必须在验证通过后，直接交给同一个获准环境。** 如果先在外部网关解密，网关已经看到了原文。

**证书确认“谁签的”，测量确认“什么环境”，通道绑定确认“数据交给谁”。三者缺一不可。**

### 开源、构建和证明，要对应起来

测量值与批准值一致，说明被测量的内容符合批准条件；软件会不会过度记录数据、有没有危险出口，还要看代码与配置。

源码让客户能够审查；可复现构建是按约定的源码与构建条件重建出字节一致的程序产物，帮助确认源码对应哪个程序；远程证明再把批准对象与实际连接的环境对应起来。闭源程序也可以核对身份，但客户自行审查行为的能力更有限。

客户固定批准值与自动接受厂商更新，承担的信任不同。前者控制接受范围，后者还要信任厂商的后续发布决定。

**TEE 可以缩小信任范围，但仍依赖硬件体系和获准软件。可验证，也不等于没有漏洞。**

## FHE：一直计算密文，最后由客户解密

### 为什么不知道内容，也能计算

FHE 专门设计密文的数学结构，让密文运算对应明文运算。以精确加法为例，对“3 的密文”和“5 的密文”执行同态加法，客户解密结果得到 8，服务器全程不必知道这些数值。近似数值方案则在约定误差内得到结果。

加法、乘法能够组合成更复杂的计算，比较和选择也能转换成相应步骤。服务器执行约定的计算规则，解密能力留在客户手里。

<figure>
  <img src="/assets/zh/posts/20261004-confidential-ai-privacy-tee-fhe/fhe-data-flow.svg" alt="企业加密输入，服务端计算密文，企业解密结果。" width="480" height="660">
  <figcaption>计算发生在服务端，解密能力留在客户手中。</figcaption>
</figure>

客户保管私钥，按方案提供公钥和必要的求值材料。公钥用于产生密文，求值材料帮助完成特定密文运算，都不等于交出私钥。服务器直接处理已有密文，并非每算一步都要重新调用公钥加密。

**核心是密文具有可计算的数学结构：服务器算得出结果密文，却读不到内容。** 深入原理可看[同态加密概述](https://homomorphicencryption.org/introduction/)。

### 普通模型怎样变成 FHE 模型

模型权重是训练得到、决定模型如何计算的参数。普通训练得到的权重可以用于加密输入的计算，权重本身不必加密。要改造的是推理程序：把模型里的运算转换成同态运算，复杂函数必要时使用近似方法。

当数值精度和输入输出规模有限时，这些计算在理论上可以拆成 FHE 支持的基本运算。实际适配还要检查效果：近似误差可能改变 token 选择，影响后续生成。训练时无需知道客户密钥，原训练数据也不会因为推理使用 FHE 就自动受到保护。

**FHE 改造的是计算方式；能否保留模型效果，需要实际验证。** 具体适配可看 [EncryptedLLM](https://proceedings.mlr.press/v267/de-castro25a.html)。

### 下一 token 怎么生成，全程不解密怎么继续

生成过程可以分成三步：先计算加密的候选分数，再用同态比较和选择得到加密 token，最后把它转换成下一轮加密输入，与加密缓存一起继续计算。

例如，两个候选分别是 token 14 和 29。同态比较产生加密的选择条件，这个条件继续参与运算，得到 14 或 29 的密文。**服务器直接计算出所选 token 的密文，无需先知道编号，也无需解密后重新加密。**

<figure>
  <img src="/assets/zh/posts/20261004-confidential-ai-privacy-tee-fhe/fhe-encrypted-generation.svg" alt="加密分数经同态比较选择得到加密 token，再得到加密输入，与加密缓存一起进入下一轮；最后客户解密。" width="480" height="740">
  <figcaption>分数、选择结果、下一轮输入与缓存都可以保持加密，最后才由客户解密输出。</figcaption>
</figure>

实际系统还要适配随机选择 token、缓存和结束条件，并保护查询 token 对应向量时的访问过程。有些实现把部分步骤交回客户，属于交互或混合方案。

**从分数到下一轮输入，都可以保持加密，循环不必靠中途解密才能继续。** 条件选择示例见 [TFHE-rs](https://docs.zama.org/tfhe-rs/references/fine-grained-apis/boolean)。

### 现实限制：成本高，完整流程也要安全

FHE 的成本主要来自三处：密文比原数值大，同一次运算更复杂，还要执行额外步骤来维持密文可计算。大模型逐个生成 token，这些开销会逐步累积，所以长上下文、长输出和高并发都更昂贵。

评估时要测从客户加密到最终解密的完整请求，不能拿某个运算或模型单轮计算的速度，代替连续生成的体验。

FHE 的保密以相应数学安全假设、合适参数和正确实现为前提，还依赖客户端、密钥管理和完整协议。加密前的检索、分词如果已把原文交给服务端，后续 FHE 无法消除暴露。恶意服务器还可能利用解密反馈获取信息，因此客户如何处理和反馈结果也必须受控。

**FHE 已有实现，通用大模型的主要门槛是完整推理成本与适配。它保护内容，但不自动证明服务器诚实计算。** 协议风险可看 [SEAL 安全说明](https://github.com/microsoft/SEAL/blob/main/SECURITY.md)。

## 保密之外，还要管住审核与数据出口

### 看不到原文，也可以限制模型滥用

TEE 的安全模型可以在保护环境内读取明文，审核请求与输出。FHE 则可以让适配后的安全模型处理密文，得到加密的风险判断。

这个判断仍是密文，服务器不会因此自动知道用户是否违规。但它可以用加密条件控制返回内容：允许时返回答案，拒绝时返回拒绝消息，最后由客户解密。返回结果还必须清理未授权的中间信息，避免客户解密后读到本应被拒绝的答案。这种输出控制本身不保证提前省掉生成计算。

如果厂商需要据此封禁账号或提前停止计算，就要增加只披露必要审核结论的协议，并验证结论真实对应本次请求。不能依赖用户自行声称“审核通过”，也不能为审核交出输入私钥。

审核必须与同一份请求绑定并强制执行。分类器仍会误判、漏判或被绕过；已有加密分类与选择实现，也需要额外工程才能组成完整的大模型审核系统。

**不解密原文，可以计算并执行审核；让厂商读出审核结论，需要另外设计。** 隐私审核的边界见[相关综述](https://petsymposium.org/popets/2023/popets-2023-0060.pdf)。

### 数据出口和业务权限，仍由程序控制

检索文档、工具调用、日志和备用供应商，都可能把数据带出保护范围。例如，能够调用工具执行任务的 AI 智能体（Agent）被文档中的恶意指令诱导，把上下文发给外部工具，原环境证明仍可能通过。

因此，检索要遵循权限，工具和网络出口要受控，日志、缓存和重试也要执行同一数据策略。机密服务故障时，不能自动退回不允许接收该类数据的普通接口。

环境符合批准要求、结果符合约定计算、答案符合事实，是不同问题。模型仍可能编造看似可信的错误内容，也就是“幻觉”；把客户档案交给无权接收的人，也仍然是越权。输入保密也不会自动阻止用户通过输出获取模型记住的训练信息，或通过大量查询模仿模型能力。

**保密技术负责限制读取，业务程序负责授权与出口；两者都需要。** 请求长度、时间等附带信息，以及平台声明之外的攻击和停机风险，也要另行考虑。

### 其他技术各有用途

安全多方计算（MPC）让多个参与方共同完成计算，按协议限制各方获知其他方的私有数据。例如，多家公司共同统计数据，但不直接公开各自的原始记录。部分方案依赖参与方不串通，代价常在通信与交互。

差分隐私通过受控的随机机制，限制单个人的数据对结果分布的影响，降低从统计或模型结果中推断其信息的风险。可验证计算让接收方检查结果是否符合约定计算；零知识证明让一方证明某项条件成立，同时隐藏用于证明的秘密。它们不会自动隐藏计算方已经收到的原文。

**这些技术解决的问题不同，可以组合使用；没有一个名称能代表整条链路都安全。**

## 厂商现状：基础设施可用，接口要逐项判断

以下按 **2026 年 10 月 4 日** 的公开资料整理。

### 硬件与云平台

AMD、Intel 提供不同类型的机密计算与证明能力；NVIDIA 的相应 GPU 产品和模式支持机密计算。Azure、Google Cloud、阿里云已有公开的机密 GPU 部署方案，亚马逊云服务（Amazon Web Services，AWS）也提供相应的虚拟化与隔离机制。

这些能力的保护范围、可用地区、实例供应方式和配置要求不同。尤其是：**机密实例的支持，不代表任意托管模型 API 都支持客户证明。** 模型服务还需要把推理软件、模型、通信和验证流程接起来。

**硬件支持意味着可以搭建；现成接口是否具备完整保护，要看具体产品。**

### 专门服务

| 服务 | 公开方向 | 使用时看什么 |
| --- | --- | --- |
| Privatemode | 公开可信组件和构建资料，支持客户端验证 | 测量范围、模型，以及是否固定批准版本 |
| NEAR AI Cloud | TEE 模型服务与验证指南 | 实际调用的证据范围，部分能力仍有实验性限制 |
| OPAQUE | 机密环境内的检索、Agent 与分析 | 外部模型和工具出口是否另有保护 |
| Apple 私有云计算 | 隔离运行、软件透明与客户端准入 | 面向 Apple Intelligence 的具体能力 |

部分专门服务已经提供软件审查与运行验证能力。客户能验证到哪一步，取决于源码、构建证据、证明范围与更新策略，底层硬件和相关固件仍是信任基础。

**重点是本次调用能验证什么，以及客户控制接受哪些版本。**

### 普通 API 与 FHE 服务

OpenAI、Anthropic 等提供数据使用与保留政策，具体适用范围要看账户、接口和功能。这些条款可以约束供应商，但本身不证明本次推理运行在客户批准环境中。

某些功能有更具体的保护。例如，OpenAI 的 Private Safety Processing（私有安全处理）使用机密运行环境处理相应安全记录；该机制覆盖的是安全审查，原始推理链需要另外判断。

FHE 有工具与模型研究实现，但支持必须落实到具体模型、完整生成流程和实测成本。普通黑盒 API 无法由客户单方面改成全密文接口。

**选择产品，要同时看模型能力、可验证范围和完整成本，隐私条款与技术证据分别判断。**

## 企业选择：先决定能交出去什么

### 按数据要求选择部署

数据不允许外发的任务，应留在企业控制的内部环境。允许外部计算、但要求内容保密的任务，则评估是否有满足要求的机密或密文计算方案。自部署也要管权限、日志、网络和供应链，并承担算力与维护成本；部署在第三方云上，还要考虑云基础设施是否属于防范对象。

允许外发时，先在内部筛选资料、提取必要信息，再选择适合的接口：

| 要求 | 可考虑的路线 |
| --- | --- |
| 数据不允许外发 | 企业控制的内部环境 |
| 允许供应商处理明文 | 最小化数据后调用普通 API，落实用途与保留约束 |
| 信任获准软件，防范基础设施管理员 | TEE、远程证明与受保护通道 |
| 连服务端软件也不能读 | FHE、MPC 等，并评估协议条件与成本 |

**先确定谁可以读，再比较模型效果、价格和可用性。**

### 脱敏与多厂商拆分，只能减少部分暴露

姓名、账号可以换成内部代号，把映射留在企业并限制访问。但职位、时间、事件可能继续识别人，合同条款和商业计划也可能仍然敏感。脱敏还要保留完成任务所需的信息，避免结果失真。

任务可拆分、各片段本身允许外发时，多厂商可能减少单家获得的完整信息；仍要考虑关联和串通。把同一份明文发给更多厂商，反而扩大暴露面。

**脱敏和拆分是减少外发的办法，不是密码学保密保证。**

### 用统一入口执行规则

统一调用入口落实数据等级、供应商准入、必要脱敏、证明验证与结果权限，自己的日志也要受控。备用接口和重试必须遵守同一规则，不能为便宜或可用性降低保护要求。

**规则必须落实到每次请求，覆盖主路径、返回结果和故障路径。**

## 最后：哪些能验证，哪些仍需要信任

对普通第三方 API，如果缺少可审查软件、可信构建、运行证明和通道绑定，客户就无法独立核对整条推理链。应按供应商具备读取所发明文的能力来设计数据边界，再用协议约束用途与保留。

**TEE 的核心是可信测量、硬件证书链、客户批准策略和通道绑定。** 有专门服务提供软件审查与验证路径，可以按实际范围验证；硬件体系与获准软件仍需要信任。

**FHE 的核心是无需解密就能计算。** 理论可行，也已有实现，完整大模型的主要障碍是成本与工程适配，能否使用要按任务实测。

企业最直接可控的，是外发内容、调用权限和数据出口。减少外发、必要脱敏、合适的部署与验证可以组合；无法满足保密要求的任务，留在自己能控制的环境。

**最终判断只看三件事：谁能读、能验证到哪里、剩下需要信任谁。**
