两个分别位于内网的程序，怎样通过互联网直接交换数据，而不让服务器持续代转？文件传输、音视频和远程访问中的 P2P 连接经常需要解决这个问题。

难点在于建立接收路径：对方需要知道可用的地址和端口，数据包要能到达目标设备，沿途规则必须允许通过，目标程序也要准备接收。UDP 打洞借助服务器交换地址，再用主动探测尝试建立这样的直接路径；网络不支持直连时，可以使用中继。

## 一、直接通信需要怎样的接收路径

### 私有地址不能直接作为公网接收地址

以使用 IPv4 NAT 上网的家庭网络为例。电脑 A 的地址是 `192.168.1.10`，路由器连接公网一侧的地址是 `203.0.113.10`：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/ipv4-nat-network.svg" alt="电脑 A 经家用 NAT 网关访问公网，私有地址与网关公网地址处于不同作用域。" loading="lazy" width="640" height="476">
  <figcaption>家庭 IPv4 NAT 网络</figcaption>
</figure>

`192.168.1.10` 是私有地址，可以用于相应的内部网络，但不能直接作为公网路由的目标。外部设备需要另一个能够到达 A 的接收地址。

这个网络中的路由器除了转发 IP 数据包，还执行 NAT，将私有地址转换为外部可用的地址。NAT 是网关具备的一项功能，并不是所有经过路由器的通信都需要转换地址。

### 地址转换提供了什么

一台电脑可以同时运行多个网络程序。IP 决定数据发往哪个网络地址，端口号则参与区分设备上的通信入口。假设 A 上的程序使用本地端口 `50000` 向公网服务器发送数据，网关可能进行这样的转换：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/nat-source-mapping.svg" alt="网关将内部来源 192.168.1.10:50000 转换为 203.0.113.10:62000。" loading="lazy" width="640" height="392">
  <figcaption>出站数据的来源转换</figcaption>
</figure>

NAT 保存这份内外地址的对应关系。发往 `203.0.113.10:62000` 的数据，如果匹配有效映射且满足入站规则，就可以被转换为发往 `192.168.1.10:50000`，再转给 A。到达 A 后，由 A 的操作系统交给相应的接收程序。

**地址转换解决“转给谁”，过滤规则解决“允许谁通过”。** 同一台家用网关经常同时执行这两项工作，但两者是不同的功能。已有映射不代表任意来源都会被放行，数据到达设备也不代表目标服务已经可用。

### 为什么知道外部地址仍不够

假设 B 得知 `203.0.113.10:62000`，向这里发送数据。要让它真正到达 A 的程序，至少需要满足三项条件：

- 外部地址和端口仍然对应 A 使用的内部地址和端口，相关映射没有失效。
- NAT 的来源过滤、沿途防火墙及 A 的主机防火墙，允许这次通信。
- A 上有程序在相应地址和端口接收数据，并接受相应协议的通信。

对于需要按目标分配映射的 NAT，A 访问服务器时使用的外部 IP 或端口，还可能不同于它访问 B 时使用的结果。B 从服务器获知的地址，因而未必适用于双方直连。

NAT 穿透重点解决的是外部地址和可用路径怎样建立。它不能代替应用启动接收服务，也不能让流量绕过仍然生效的访问规则。

## 二、让内网设备互通的几种办法

### 已经能直接访问，就使用已有路径

两台设备在同一个局域网，且彼此没有被隔离时，可以使用局域网地址通信，不需要经过公网打洞。

如果接收方有可用的公网地址、目标程序正在接收，而且路由和防火墙规则允许访问，就可以尝试直接连接。

只有一方可直接访问时，可以让另一方主动连接它。即使业务上是外部设备想联系内网设备，也可以先经协调通道通知内网程序，由内网程序发起底层连接。业务由谁发起，与底层连接由谁主动建立，不必相同。

### 让路由器明确转发到内部设备

能够管理路由器时，可以直接配置：收到公网某个端口的数据后，转发给指定的内网地址和端口。例如：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/port-forwarding.svg" alt="端口转发将网关外部端口60000收到的数据转给内部设备端口50000。" loading="lazy" width="640" height="510">
  <figcaption>明确配置入站转发</figcaption>
</figure>

这就是端口转发：它明确了外部地址应该转换到哪个内部地址和端口。目标程序仍需在对应端口接收，网关与主机的防火墙也要允许这股流量。部分设备会在配置转发时一并设置放行规则，具体取决于实现。

这种方式直观，但需要有权配置相关路由器。如果家用路由器外面还有运营商的地址转换，仅配置家用路由器这一层通常不够。

### 双方都主动向对方发包

两边都没有现成的入站路径时，可以先交换候选地址，再各自向对方探测。对于要求内部先联系过该来源的网关，这些出站包有机会建立允许后续来包的状态；地址映射也必须适用于对端。

这就是常见的打洞思路，包括 UDP 打洞和 TCP 打洞。双方主动探测是处理这类网络限制的方法，并非所有直接通信都需要的步骤。

### 通过服务器代为转发

如果双方无法直接互通，但都能连接一台公网服务器，就可以让它代为传递业务数据：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/relay-path.svg" alt="设备 A 和设备 B 分别连接中继服务器，业务数据经中继转发。双方分别建立可用的通信路径" loading="lazy" width="640" height="492">
  <figcaption>通过服务器转发</figcaption>
</figure>

这就是中继。它不要求 A、B 之间存在直接路径，但业务数据持续经过服务器，需要消耗服务器带宽，也增加了网络和运维依赖。中继自身仍要可达并且正常运行。

P2P 系统可以借助服务器发现对方、交换地址，也可以让服务器提供中继路径。业务是否直连、何时切换，由实际可达性和连接策略决定；直接探测与中继通信也可以同时进行。

| 方式 | 怎样建立路径 | 主要限制 |
|---|---|---|
| 直接访问 | 使用原本可达的地址 | 网络和服务允许访问 |
| 端口转发 | 明确配置路由器的转发关系 | 需要管理相关路由器 |
| 打洞 | 双方主动发包，建立可用状态 | 依赖两端路由器和网络行为 |
| 中继 | 由双方都能访问的服务器传递数据 | 占用中继资源，依赖中继可用 |

## 三、一次 UDP 打洞是怎样完成的

### 双方先向公网服务器发送数据

UDP 允许程序向指定的 IP 和端口发送独立数据报，无须先完成传输层连接握手。它不提供交付确认，也不要求应用逐包应答。打洞程序为了检查双向路径，会自行发送探测消息并检查相应的应答。

假设电脑 A 和电脑 B 分别位于两个网络中，还有一台双方都能访问的公网服务器 S：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/rendezvous-server.svg" alt="电脑A和B分别通过自己的NAT网关向公网服务器S发包，S观察并交换外部端点。" loading="lazy" width="640" height="560">
  <figcaption>双方先联系公网服务器</figcaption>
</figure>

A、B 上的探测程序各自使用一个固定的本地 UDP 端口，并准备接收对端的探测包；主机防火墙允许相应流量。它们向 S 发送数据后，S 根据收到的数据包观察到 NAT 转换后的来源：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/observed-endpoints.svg" alt="设备A本地端点映射为203.0.113.10:62000；设备B本地端点映射为198.51.100.20:63000。上方为本地端点，下方为服务器观察结果。" loading="lazy" width="640" height="606">
  <figcaption>服务器观察到的外部端点</figcaption>
</figure>

这个过程假设：A、B 随后改为向彼此发包时，各自路由器仍使用图中的外部地址和端口，且网络允许必要的 UDP 通信。如果外部地址发生变化，就需要额外探测，不能直接套用这组结果。

### 服务器把双方的外部地址交给对方

S 把 `198.51.100.20:63000` 交给 A，把 `203.0.113.10:62000` 交给 B。双方由此知道可以向哪里尝试发包。

此时 S 只是交换连接信息。A、B 已经知道探测目标，但还不能据此认定彼此可达。

### 双方主动发包，让返回数据有机会通过

A 向 `198.51.100.20:63000` 发包，B 向 `203.0.113.10:62000` 发包。

假设两边都要求“这个内部地址和端口先联系过外部的 IP 和端口，才允许该来源发回数据”。在这种规则下，A 的出站包建立或刷新 A 端的相应状态，B 的出站包建立或刷新 B 端的相应状态。第一次发送可能发生这样的情况：

1. A 先发，路由器 A 已有联系 B 的记录，但路由器 B 还没有联系 A 的记录，A 的包被 B 端丢弃。
2. B 随后发包，建立自己的出站记录。它发来的包有机会通过已经准备好的路由器 A，到达 A。
3. A 重试或回复时，路由器 B 已有相应记录，这次也能让数据通过。

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/udp-hole-punching.svg" alt="A / 路由器 A与路由器 B / B按时间从上到下交互。① A 首次探测 B，A 端已有状态；B 端尚未放行，丢弃；② B 主动探测 A，B 端建立状态；数据有机会到达 A；③ A 重试或应答，B 端已有相应状态，允许通过；④ 双向直接通信，验证探测应答后，沿用这些 UDP 端点。前提：映射适用，过滤与网络策略允许" loading="lazy" width="640" height="680">
  <figcaption>UDP 打洞：出站探测与重试</figcaption>
</figure>

**在这组过滤条件下，双方的出站包分别建立各自所需的放行状态。** 数据包不必严格同时发出，适当的重试可以处理先后顺序和丢包。

### 收到并验证应答后，使用直接路径

A、B 需要使用能够识别和验证的探测消息，确认收到的应答确实属于这次通信。确认双向路径可用后，业务数据就可以直接在双方之间传输，S 无须持续代转这些数据。后续传输沿用参与探测的 UDP 本地地址、端口和对端地址；其他端口或协议的可达性需要另行验证。

UDP 本身没有“连接建立成功”的状态，收到一个包也不代表今后一直可达。程序需要保留相应的收发端口，并管理后续探测和超时。

从查询外部地址到打洞、再到传输数据，本地源 IP 和端口通常要保持一致。程序换了源地址或端口，路由器就可能建立另一份记录，使刚才获知的外部地址失效。

### 空闲和网络变化后，路径还要重新确认

路由器的记录不是永久的。连接长时间没有流量时，相关状态可能过期；Wi-Fi 切换、设备休眠或 IP 改变，也可能使旧地址不再可用。

因此，P2P 程序通常要做三件不同的事：用适量的保活流量维持需要的状态，用应答和超时判断路径是否还在工作，失效后重新发现地址并尝试连接。

打洞成功解决的是一次可达性问题。稳定通信还需要持续维护状态，并准备在直接路径不可用时使用中继。

## 四、打洞的网络条件与配套协议

### 同一对设备，为什么换个网络就不行了

有些网关向不同目标发包时复用相同的外部 IP 和端口，有些会随目标改变其中一项；对收到的数据，它们允许的来源范围也可能不同。这两种差异分别称为映射行为和过滤行为。一个 IP 和端口的组合称为端点，内部端点与外部端点的对应关系，就是一份地址映射。家用网关通常同时转换地址和端口，这类转换也称为 NAPT。

映射决定地址如何转换，以及这份转换关系能否被其他通信复用。过滤决定一个外部来源的数据包能否进入已有映射。家用路由器通常同时处理地址转换与入站过滤。

#### 映射：外部地址是否会随目标变化

假设 A 保持同一个 UDP 本地端点，先向服务器 S 发包，再向设备 B 发包。路由器会不会继续使用 `203.0.113.10:62000`，取决于映射规则：

| 映射规则 | 怎样复用已有映射 |
|---|---|
| 与目标无关，EIM | 访问不同目标 IP、端口时都复用 |
| 依赖目标 IP，ADM | 目标 IP 相同则复用，目标 IP 改变则使用不同映射 |
| 依赖目标 IP 和端口，APDM | 目标 IP、端口都相同则复用，任一改变则使用不同映射 |

这些规则都以同一传输协议、同一本地端点、原映射仍有效为前提。对于打洞，最方便的是第一种：服务器看到的外部端点，也能用于 A 与 B 的通信。后两种情况下，A 转而向 B 发包时可能使用另一个外部端点，B 手中的地址就可能不适用了。

外部地址一旦依赖目标，服务器 S 看到的地址就可能无法直接复用。例如 A 访问 S 时使用外部端口 62000，访问 B 时却换成 62001，B 继续探测 62000，就可能无法建立双向路径。

#### 过滤：允许哪些外部来源进入

即使外部映射没有改变，路由器也可能要求 A 先向某个来源发过包，才接收它的来包：

| 过滤规则 | 哪些外部来源可以进入对应映射 |
|---|---|
| 与来源无关，EIF | 不限制外部源 IP 和端口 |
| 依赖来源 IP，ADF | A 先向该 IP 发过包，才允许它发回来 |
| 依赖来源 IP 和端口，APDF | A 先向该 IP、端口发过包，才允许它发回来 |

出站记录属于对应的本地端点，也有有效期。路由器允许之后，包还要经过其他网络设备和主机防火墙，最终才能交给应用。

过滤规则要求精确匹配 IP 和端口，也不单独意味着打洞失败：双方主动发送正是在建立对应状态。能否成功，要结合两边的映射、过滤以及主机和网络策略判断。某些目标相关映射可以通过实际端点学习或额外探测处理，但探测需要限制时间和资源，并准备中继。

### 多层 NAT、同一网关与 IPv6

有些家庭网络外面还有一层运营商 NAT，也就是 CGNAT：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/nested-nat.svg" alt="设备访问公网时依次经过家用NAT与运营商CGNAT，服务器观察到最外层转换结果。" loading="lazy" width="640" height="584">
  <figcaption>多层地址转换</figcaption>
</figure>

这时，家用路由器的外部地址还不是真正的公网地址。数据包经过运营商网络时会再被转换一次，公网服务器看到的是最外面那层转换的结果。

打洞需要整条路径配合：每层映射怎样复用、允许哪些来源、多久过期，都会影响结果。CGNAT 表示运营商部署了共享地址转换，并不指定某一种映射或过滤规则，所以多层 NAT 有时能够穿透，有时会成为障碍。

如果两台设备位于同一 NAT 后面，却使用彼此的外部映射通信，还可能依赖网关把包转回内部的能力，称为 Hairpinning。使用公网映射端点，也不代表包一定离开本地网络。

双方具有可用的全球单播 IPv6 地址时，可能不需要 IPv4 NAT 转换，但网关和主机仍可能限制入站通信。局域网、IPv4、IPv6 都可以提供直接路径，最终仍要检查实际可达性。

对于支持自动端口映射的网关，应用还可以通过 PCP、NAT-PMP、UPnP IGD 等机制请求映射。它们依赖相关网关支持和策略许可，无法仅靠家用路由器上的配置控制上层运营商网关。

### STUN、ICE 和 TURN 怎样配合

地址查询、多个路径的检查、中继资源的申请，可以由通用协议提供。STUN、ICE、TURN 分别处理这些工作。

**查询外部地址：STUN。** 客户端向服务器发送 Binding 请求，可以获知服务器看到的请求来源。这个结果反映的是一次具体通信所使用的映射。STUN 也可以用于端点之间的连通性检查和保活，但设备发现、连接信息交换、路径选择和业务安全还需要应用或其他协议负责。

**检查并选定路径：ICE。** 一台设备可能有局域网地址、IPv6 地址、通过 STUN 得到的映射地址，以及 TURN 提供的中继地址。ICE 交换已经获得的候选，再检查本地与远端地址的组合；检查过程中还可能发现新的地址，最终选定可用的组合。

ICE 中常见的候选有四种：

| 候选类型 | 地址从哪里来 |
|---|---|
| Host | 本机网络接口 |
| Server-reflexive | 与 STUN/TURN 服务器通信时发现的映射 |
| Peer-reflexive | 与对端检查连通性时发现的新地址 |
| Relayed | TURN 分配的中继地址 |

ICE 的连通性检查使用 STUN。最终使用哪一组地址，要遵循候选优先级和连接选择规则，目的在于建立合适的可用连接，而非保证找到所有网络条件下的最低延迟路径。

**分配并使用中继：TURN。** 客户端取得中继地址，设置相应许可后，通过服务器与对端交换数据。它可以参加 ICE 的候选选择，也可以被独立使用。

TURN 中要区分“客户端到中继”和“中继到对端”两段：基础 TURN 允许客户端经 UDP、TCP、TLS-over-TCP 或 DTLS-over-UDP 访问服务器，而服务器到对端使用 UDP；中继到对端的 TCP 分配由另外的扩展定义。因此，使用 TCP 访问 TURN 服务器，只说明第一段使用 TCP。

STUN 提供探测工具，ICE 组织地址检查与选择，TURN 提供可选的中继路径。某个产品也可以根据自己的需求实现连接管理，不一定完整采用标准 ICE。

### TCP 打洞为什么需要额外的配合

TCP 打洞还需要处理连接建立的状态。TCP 除了常见的一端主动连接、另一端监听，也支持双方都主动发起的“同时打开”。SYN 表示发起连接，SYN+ACK 则在发起连接的同时确认对方的请求。当双方 SYN 在途中交错，收到对方 SYN 后，各自回复 SYN+ACK，确认对方的初始序列号，最终进入已建立状态。

双方同时打开的报文交互可简化为（省略重传）：

  <figcaption>TCP 同时打开 · 简化交互</figcaption>

TCP 打洞可以利用这种机制，但需要额外解决几个问题。双方要获得适用于 TCP 的外部地址，安排合适的本地绑定和重试时机；网关则要允许符合这次连接状态的对方 SYN 通过。UDP 和 TCP 的映射通常分别管理，所以 UDP STUN 得到的地址不能直接当作 TCP 的可用地址。

在程序实现上，向服务器建立的 TCP 连接与向对端建立的连接属于不同 Socket，能否复用所需本地端点还取决于系统 API。ICE-TCP 因此区分主动连接、被动接收和同时打开等候选，不是所有 TCP 候选都依靠双方同时发送 SYN。

TCP 打洞适合被作为一种候选方案评估，尤其是需要原生 TCP P2P 连接的应用。UDP 被封锁时也可以考察它，但前提是网络确实允许访问对端：浏览器能访问 HTTPS，有时只是因为网络允许指定服务器或要求经过代理。这样的环境中，连接一个允许访问的 TCP/TLS 中继，往往更现实。

| 比较项 | UDP | TCP |
|---|---|---|
| 交付方式 | 独立数据报 | 有序字节流 |
| 连接与验证 | 应用自行确认路径和会话 | 传输层建立连接 |
| 丢包处理 | 由上层按业务需要决定 | TCP 重传并按序交付 |
| 穿透条件 | 映射、过滤与有效期配合 | 还需要网关正确处理 TCP 状态及建连报文 |
| 常见用途 | 实时通信、VPN、基于 UDP 的应用协议 | 需要可靠字节流的应用 |

UDP 便于上层选择传输方式：音视频可以优先考虑时延，VPN 可以直接承载 IP 数据包，文件传输则可以使用成熟的可靠传输协议。相应地，UDP 应用需要根据业务处理丢包和排序，并根据网络拥堵情况控制发送速度，性能也取决于实现与网络条件。

### 打洞之外，还需要身份认证和数据保护

探测收到应答，说明当时有一条通信路径；要传输业务，还需要确认应答来自预期设备，验证它是否有权访问目标服务，并保护后续数据。

因此，P2P 系统通常将身份认证、访问授权和安全传输一起设计。密钥协商用于建立会话密钥，加密与完整性校验用于保护内容，防重放机制则防止捕获的旧数据包再次生效。直连和中继都可以承载加密数据，路径的选择本身不提供这些安全能力。

## 五、Tailscale 的 P2P 连接与加密隧道

Tailscale 给加入同一网络的设备分配虚拟 IP。应用向虚拟 IP 发起通信，Tailscale 负责寻找实际路径，并在直连和中继之间切换。设备之间的数据由 WireGuard 加密隧道保护。

### 应用使用虚拟地址，底层寻找实际地址

假设 A、B 加入同一个 Tailscale 私有网络，也就是 Tailnet，分别获得 `100.64.0.1` 和 `100.64.0.2`。这些地址属于 Tailscale 使用的虚拟网络，应用用它们标识目标设备。底层直连使用对端可达的局域网或外部地址；走中继时，则使用可达的中继及其转发信息，将数据送到对端。

以 B 运行系统 SSH 服务、未启用 Tailscale SSH 接管为例，在 A 上执行：

```bash
ssh user@100.64.0.2
```

A 的 SSH 客户端会向 B 的虚拟地址发送 TCP 数据。普通系统网络模式下，这些 IP 数据包经过虚拟接口交给 Tailscale 加密。直连时，加密数据发往 B 的实际端点；走中继时，则先发往中继，由中继送到 B。B 解密后，将原来的 IP 数据包交给本机协议栈和 SSH 服务。启用 Tailscale SSH 时，发往 Tailscale IP 的端口 22 流量由 `tailscaled` 接管，不能直接套用系统 SSH 服务的接收路径。

在 UDP 直连路径上，数据的封装与交付关系是：

  <figcaption>SSH 经 UDP 直连隧道传输</figcaption>

内层虚拟地址供应用使用，外层实际地址负责将加密数据送到设备。网络切换时，Tailscale 可以重新寻找外层路径，应用仍使用原来的虚拟地址。切换中断过久时，上层连接仍可能超时。

`100.64.0.0/10` 是共享地址空间，这些虚拟地址不等于设备的公网地址。Tailscale 也支持 IPv6。另外，在没有 TUN 权限的环境中，可以运行用户态网络模式，通过 SOCKS5、HTTP 代理等方式向应用提供访问。

### 控制面负责管理，数据面负责传输

设备之间要安全通信，首先要知道对方是谁、持有什么公钥，以及哪些访问被允许。这些管理和协调工作属于控制面，包括设备注册、节点信息、公钥及访问策略的分发。

真正承载业务的数据面则负责加密、发送、接收、解密和路径切换。把两者分开后，控制服务器负责帮助设备建立可信关系，业务数据通常不需要经过它转发。

寻找实际路径时，Tailscale 会收集本地地址、通过 STUN 观察外部映射，并使用自己的发现协议 DISCO 与对端交换探测消息。DERP 中继除了传输加密业务数据，也能传递这些发现消息，帮助双方协调直接探测。

### 新路径怎样建立，又怎样切换

当 A 还没有到 B 的可信直接路径时，通常可以先借助 DERP 交换信息并提供初始通信，同时探测可能的 UDP 直接路径。找到可用直连后，后续业务便切换到直接路径；直连不可用时，可以使用满足条件的 Peer Relay，或者继续经 DERP 传输。

直接路径探测与中继通信可以同时进行。A 已经有可信的直接路径时，可以直接复用，也不需要为每条新的 SSH、HTTP 连接重新做一遍发现。

同一局域网内，如果双方私网地址可达，Tailscale 可以直接通过局域网传输加密数据。这条业务路径不需要经过公网 NAT 或中继。不同 VLAN、主机防火墙和无线客户端隔离，仍可能使看似同网的设备无法直接访问。

### Peer Relay 与 DERP 分别适合什么网络

Peer Relay 是由用户在 Tailnet 中指定设备承担中继。比如 A 和 B 无法直接互通，但都能通过 UDP 访问一台网络条件较好的公司服务器，就可以借它转发：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/peer-relay.svg" alt="设备 A 和设备 B 分别连接Peer Relay，业务数据经中继转发。双方均需通过 UDP 到达配置端口" loading="lazy" width="640" height="492">
  <figcaption>Peer Relay 的两段 UDP 路径</figcaption>
</figure>

部署时需要配置中继服务端口，确认双方都能访问，并授予 `tailscale.com/cap/relay` 等所需权限。中继设备也要具备足够的带宽和处理能力。它解决的是“两端之间直连困难，但两端到中继可达”的问题；客户端完全无法使用 UDP 时，这条路径也无法成立。

DERP 通常通过 TCP/TLS 443 提供中继。它在直接 UDP 不可用的网络中尤其有用，前提是客户端仍能访问 DERP 服务。默认网络由 Tailscale 运营，也可以自行部署。

| 对比项 | Peer Relay | DERP |
|---|---|---|
| 常见部署方式 | 用户指定的 Tailnet 设备 | 官方提供，也支持自建 |
| 客户端访问中继的方式 | 指定 UDP 端口 | 通常使用 TCP/TLS 443 |
| 适用条件 | 双方都能通过 UDP 到达中继 | 双方能够访问 DERP 服务 |
| 主要成本 | 自建节点的网络、CPU 和运维 | 中继路径、服务容量及相应传输开销 |

Tailscale 优先使用可用直连，并在中继方案中优先考虑满足条件的 Peer Relay。这是路径选择上的偏好；实际建连中，DERP 可以从一开始就参与，而非等所有其他尝试结束后才接入。

所有中继都增加了额外的网络依赖。实际延迟和吞吐量要结合两段路径测量，某条中继路径也可能因为路由条件较好而表现优于另一条直接路径。

### 加密保护到哪里

WireGuard 是一种加密 IP 隧道协议。它使用公钥握手建立会话密钥，加密数据并校验其完整性，防止旧数据包被重复接受。Tailscale 再把设备公钥与身份、访问策略结合起来。这样既能确认通信对象，也能控制它有权访问哪些服务。

Peer Relay 和 DERP 转发的是双方之间的加密数据，不需要解密业务内容。不过，中继仍能观察到它服务的连接及流量时间、大小等信息，也可能因为故障、拥塞或丢包影响通信。

子网路由器和出口节点承担的是另一种职责：它们作为隧道的一端解密，再向其他网络转发。数据离开这些节点后，要依靠 HTTPS 等协议保护后续链路。判断安全范围时，应看加密隧道在哪里结束。

### 为什么 UDP 隧道能传输可靠的 SSH

直接路径使用外层 UDP，而 SSH 的内层 TCP 仍然执行正常的连接管理、确认、重传、流量控制和拥塞控制。外层丢了一个数据包，内层 TCP 可以通过自己的机制检测并重传。

因此，WireGuard 无须把整个隧道做成一条可靠字节流，就能承载 TCP 应用。它也能同时承载 UDP 音视频等业务，让不同上层协议保留各自的传输方式。持续丢包或断链依然会降低速度，甚至使 TCP 超时失败。

走 DERP 时，外部传输还包含中继使用的 TCP/TLS。那一段的有序重传可能让后续数据一起等待，从而影响多个内层业务的时延。排查性能之前，先确认实际使用哪条路径，往往比先调整参数更有效。

### 用诊断命令观察实际路径

选路结果、隧道状态和目标服务需要分别验证。排查时先确认实际路径，再检查业务访问，最后测量性能。

#### 第一步：确认当前走哪条路径

先查看节点状态，再对目标设备做探测：

```bash
tailscale status
tailscale ping <设备名称或 Tailscale IP>
```

一次探测可能先后使用以下路径（示意输出）：

```text
pong from mac-mini (100.64.0.2) via DERP(lax) in 80ms
pong from mac-mini (100.64.0.2) via peer-relay(192.168.1.30:40000:vni:1) in 5ms
pong from mac-mini (100.64.0.2) via 192.168.1.20:41641 in 1ms
```

括号里的 `100.64.0.2` 是目标的 Tailscale IP，`via` 后面是该次探测使用的实际路径。探测可能从 DERP 切到 Peer Relay，再切到直接端点，也可能直接复用已有路径，或一直保持中继。

若 A、B 的私网地址在同一局域网内可达，`via 192.168.1.20:41641` 表示该次探测通过局域网直连。如果是 `via 203.0.113.10:62000`，则表示向这个外部端点直接发包。具体数据经过哪些网络，还要结合拓扑：私网地址也可以跨企业路由访问，公网映射则可能经过 Hairpin 回到内部。

#### 第二步：把路径探测与业务验证分开

默认 `tailscale ping` 使用 DISCO，主要检查 Tailscale 发现路径的通信。SSH 仍然可能因为访问策略、主机防火墙、没有监听或认证失败而不可用。

可以按层次继续测试：

| 测试 | 主要检查什么 |
|---|---|
| `tailscale ping <peer>` | DISCO 发现通信及路径 |
| `tailscale ping --tsmp <peer>` | 经过 WireGuard 隧道的消息，绕过对端操作系统 IP 栈 |
| `tailscale ping --icmp <peer>` | ICMP 层面的连通性 |
| SSH、HTTP 等实际请求 | 对应服务的访问与响应 |

例如排查 SSH：

```bash
tailscale ping mac-mini
tailscale ping --tsmp mac-mini
tailscale ping --icmp mac-mini
ssh -vv user@100.64.0.2
```

这些测试是在缩小问题范围。路径探测有响应、业务却失败时，就应继续看隧道、主机和服务；ICMP 被单独限制时，TCP 服务也仍可能正常。使用 Tailscale SSH 的场景，还需要检查它自己的访问策略。

#### 第三步：用 netcheck 了解本地网络

```bash
tailscale netcheck
```

这个命令帮助观察 UDP、IPv4/IPv6、映射变化和 DERP 延迟。几个常用字段可以这样读：

- `UDP: true`：本次检查成功完成过 UDP STUN 往返，说明至少这条 UDP 探测路径可用。
- `MappingVariesByDestIP`：访问不同 IPv4 STUN 目标时，观察到的外部 IP 或端口是否变化。
- DERP 延迟：当前设备到相关服务的探测结果，可以作为选择和排查路径的线索。

报告反映的是已完成的探测。要判断 A、B 能否直连，仍需让它们实际互相测试；经中继访问 B 的完整时延，也包含另一端的路径和中继处理。

同时确认使用的端口和方向。常见数据端口是 UDP 41641，但实际本地端口会受平台、发行方式和配置影响，公网端口又可能被 NAT 改写。STUN 通常访问服务端 UDP 3478，DERP 通常使用 TCP/TLS 443，Peer Relay 则使用配置的 UDP 端口。

控制连接有自己的建连策略，包括使用 TCP 80 上的加密传输、不可用时回退 TCP 443 的路径。配置防火墙时，需要区分控制服务、中继和对等直连，并确认实际监听与连接目标。

#### 第四步：连接正常后，再测性能与稳定性

直连和中继说明的是数据路径，速度还取决于链路、设备和程序。可以在版本、负载和网络条件尽量一致时，比较基线路径与 Tailscale 路径，再分别测试上传、下载、单连接、多连接和持续传输。

配合观察 CPU、网卡流量、丢包和队列，更容易区分“链路跑满”与“设备处理不过来”。如果小探测包正常，大数据传输却异常，还应检查 MTU、路径 MTU 发现和封装带来的报文大小变化。

## 六、UDP 通信的并发与性能

UDP 隧道可以通过同一个外层端口承载多个业务。它们能否并行处理、传输速度能有多快，取决于 Socket 缓冲、任务调度、CPU 和网络链路。

### 端口、Socket、业务流与路径

SSH、文件传输和音视频可以共用外层 UDP 端口，但仍保留各自的连接与业务状态。业务如何分发、数据经过哪些资源，涉及四个不同层次：

| 概念 | 可以怎样理解 |
|---|---|
| 端口 | 与 IP、传输协议一起，用于识别通信端点 |
| Socket | 程序收发数据的通信对象，带有相应状态和缓冲 |
| 业务流 | 一条 SSH 连接、一次文件传输使用的连接等 |
| 网络路径 | 数据实际经过的网卡、路由器和链路 |

一个 UDP Socket 可以收发大量数据报，也可以与多个远端通信。比如一个绑定 `0.0.0.0:41641`、未限定单一对端的 Socket，在网络和系统规则允许时，可以接收多个来源的数据。应用根据来源地址和协议中的标识，将它们交给相应逻辑。

`0.0.0.0` 表示绑定时不限定本机某一个 IPv4 地址。程序也可以不显式绑定，由系统首次发送时自动选择端口；打洞场景通常会管理这个端点，尽量保持稳定。

UDP 还可以调用 `connect()` 设置默认对端。这个调用不执行 TCP 式握手；在 Linux 中，它也会限制正常接收的数据来源。调用成功表示本地关联已设置，是否能够通信仍要靠实际发包和应答确认。

### 多个内层连接如何共用隧道

A、B 之间可以同时运行多个业务：

  <figcaption>多个业务共用外层隧道</figcaption>
</figure>

这些业务各自维护需要的状态。内层数据包经过隧道封装，通过外层路径发送；对端去掉封装后，再根据内层 IP、协议和端口交给对应应用。使用 WireGuard 等加密隧道协议时，传输还包括加密与解密；UDP 本身不提供这种保护。

共用一个外层端口，并不要求 SSH 完成后才能传文件。它们可以交错发送和接收，应用也可以用不同线程处理协议解析与业务。与此同时，它们共享链路带宽、部分队列和 CPU，一个业务占满资源时，其他业务仍会受到影响。

### 并发存在，瓶颈也可能存在

常见的内核 UDP 收包路径包括协议处理、过滤、Socket 分发、接收缓冲和应用读取等环节：

  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/udp-receive-pipeline.svg" alt="UDP数据依次经过网卡队列、IP和UDP处理、Socket缓冲、应用读取与业务处理；每个环节均可能成为瓶颈。" loading="lazy" width="640" height="702">
  <figcaption>常见的内核 UDP 接收路径</figcaption>
</figure>

应用需要及时读走数据，缓冲满了可能丢包。某个读取循环、锁或工作线程处理不过来，也会限制总速度。异步 I/O 可以减少等待，多个工作线程可以分担计算，但两者都需要与实际处理流程配合。

网卡多队列同样需要结合外层流来理解。Linux 的 RSS 通常根据数据包地址和端口等字段计算哈希，将同一流送到同一接收队列。多个内层业务封装后，如果外层五元组相同，网卡可能将它们作为一个流处理。五元组指源 IP、源端口、目的 IP、目的端口和传输协议。

因此，业务能够同时运行，与接收处理是否充分分散到多核，是两个需要分别观察的问题。进一步分流取决于网卡、驱动、内核配置和应用设计。

### 多 Socket 与批量处理能改善什么

如果瓶颈在共享接收缓冲或任务分配，增加 Socket、拆分队列和工作线程可能有帮助；如果瓶颈是系统调用太频繁，批量收发可能更有效。这些优化对应的是不同开销。

Linux 的 `recvmmsg()` 可以用一次系统调用读取多个报文。GSO/GRO 则通过延后分段、聚合处理等方式减少部分逐包开销。这类机制是否能够启用，取决于具体平台、版本和数据路径。

多个 Socket 还可能复用同一本地端口，但必须遵循操作系统的绑定和分发规则。例如 Linux 的 `SO_REUSEPORT` 可以将收到的包分配给一组 Socket，而非简单地复制给每个成员。同一流是否会被分散，也取决于实际分发机制。

优化前最好先确认问题在哪里：

| 观察结果 | 主要检查方向 |
|---|---|
| 一个 CPU 核心饱和 | 收发循环、加密、协议处理和锁争用 |
| 系统调用和逐包开销明显 | 批量 I/O、分段和聚合能力 |
| 接收丢包或排队延迟上升 | 缓冲、处理速度和队列调度 |
| 接收队列负载不均 | 流哈希、网卡和内核分流配置 |
| 出口带宽已满 | 限速、公平性和可用链路容量 |

### 多路径怎样增加可用带宽

多个 Socket 如果仍经过同一个出口，最终会共享那条链路：

<figure>
  <img src="/assets/zh/posts/20261102-nat-traversal-p2p-tailscale/shared-egress.svg" alt="多个Socket通过同一个出口使用共享链路；多开Socket不会增加已饱和链路的容量。" loading="lazy" width="640" height="499">
  <figcaption>多 Socket 仍可能共享瓶颈</figcaption>
</figure>

多条路径如果能够利用额外的可用容量，就可能提高总吞吐量，例如分别使用两个网络出口。路径不必全程独立，关键在于它们共享哪些瓶颈，以及流量能否被合理分配。

即使只有一条路径，消除程序处理或队列瓶颈也可能提高实测吞吐量；如果共同出口的链路容量已经用满，多开 Socket 则不会增加这条链路的容量。

应用可以将不同业务分到不同路径，也可以用专门协议让一个逻辑连接跨多条路径传输。后者还需要处理调度、拥塞、乱序、重传和路径失效，Multipath TCP 就是这样的协议设计。

路径发现、故障切换和带宽聚合分别解决不同问题。一个系统能够发现和切换路径，并不表示它会把 Wi-Fi 与有线网络的带宽叠加起来。增加 Socket 则主要是程序和系统层面的优化，也不会自动产生额外链路容量。

## 七、P2P 系统的设计与连接恢复

P2P 系统需要同时管理设备身份、通信路径和传输状态。连接建立后，网络切换、映射过期和设备休眠仍会使路径失效，连接恢复需要与正常传输一起设计。

### 把连接管理与业务传输分开

应用要使用什么业务协议，与底层怎样建立路径，可以通过清晰的模块接口分开。这样，网络切换、重新打洞或退回中继时，就不必让每个业务重新实现同一套逻辑。

| 模块 | 主要职责 |
|---|---|
| 控制面 | 注册设备、认证身份、分发公钥、授权、交换节点和地址信息 |
| 路径管理 | 收集候选、检查连通性、打洞、选择和重建路径 |
| 数据传输 | 加密数据的收发、队列、批量处理、统计，以及发送与接收速度的协调 |
| 安全协议 | 密钥协商与更新、加密与完整性校验、防止旧数据包被重复接受 |
| 中继服务 | 转发、权限、配额、限速和资源回收 |

身份和权限应从建立会话时就考虑。候选地址交换、探测和端点更新，都需要相应的防伪造和滥用控制。已经确认“对方是谁”之后，还要判断“它能访问什么”。

如果需要标准互通，可以评估 ICE、STUN、TURN；如果构建 IP 隧道，还需要处理接口、路由、MTU 和访问控制。底层可靠传输或安全协议，优先采用成熟实现，避免将网络兼容性与协议正确性问题全部留给业务层。

### 尽早可用，再持续寻找合适路径

连接流程可以先建立一条经过认证的可用通信，再持续尝试更合适的直接路径。中继能够工作时，可以一边维持通信，一边进行有限的探测：

候选路径需要明确的优先级、探测超时、并发限制和切换条件。寻找更好路径的探测应受到限制，避免阻塞现有通信。

### 把恢复和资源限制纳入第一版设计

设备休眠、Wi-Fi 切换、IP 改变、NAT 映射过期或中继故障，都会使已有路径失效。系统要能检测中断、重新发现地址，并回收旧状态。重试也需要次数限制和退避，防止网络越差，探测流量反而越大。

传输层面还要考虑拥塞和业务公平性。如果 UDP 隧道主要承载已经进行拥塞控制的 TCP/IP 流量，而且外层发送量随内层流量变化，通常可以依靠内层对拥塞作出反应。承载缺少拥塞控制的流量，或隧道自身明显放大发送量时，则需要额外的控制措施。

运行期间需要记录诊断信息：当前使用哪条路径、何时发生切换、探测为什么失败、丢包和排队发生在哪里。P2P 系统长期维护中，能解释连接行为，与能建立连接同样重要。

## 小结

UDP 无需先建立连接就能向对端发包；UDP 打洞利用这一点，让双方从各自的本地端点主动探测，在映射适用于对端、过滤规则允许的条件下，建立并验证双向直接路径。核心是让对端发来的包匹配有效的 NAT 映射和放行状态，仅仅知道公网端口并不足够；直连不成时仍需中继。

打通 UDP 路径后，隧道可以在其上封装 IP 数据包，让多个 TCP 连接及 SSH 等业务共用外层 UDP 端点，可靠性仍由内层 TCP 等协议提供。WebRTC 则通过 ICE 选择直接或中继路径，媒体使用 SRTP，数据通道使用 SCTP over DTLS，也可以共用 UDP 端口。UDP 端口号本身不代表带宽或并发上限，多个业务可以并发共用一个端口；实际吞吐取决于链路容量、丢包、队列、CPU 和收发实现，多开端口也不会自动增加带宽。
