# 博客文章编辑与发布清单

写新文章时，先用具体问题或场景让读者知道为什么要读；再解释现象、机制、边界和实际判断。技术文章可以使用公式、图和数据，但它们要支撑相邻的论证。个人文章保留作者自己的语气与判断，不套用固定模板。

发布前人工读一遍：

1. 开头是否直接进入主题，后文是否沿着同一问题推进。
2. 关键结论有没有条件、例外和可核对的依据；图、例子和正文是否一致。
3. 链接是否贴在它支持的句子附近，读者是否知道点开要核对什么。
4. 新增段落是否与前后文衔接，是否重复已有论点或突然变成写作说明。
5. 结尾是否落在本文实际得到的判断，而非空泛口号。
6. 图片是否有帮助理解的说明，代码和公式在手机宽度下是否能阅读。

运行 `npm run check`、`npm run eval -- --changed-only --changed-file <文章路径>`、`npm run build`、`npm run check:site` 和 `npm run check:browser`。新文章把 `--changed-file` 换成 `--new-file`。CI 会自动执行这些检查，并与改动前的版本比较旧文地址；有意修改旧文 slug 时，在 `content/legacy-redirects.json` 中为原地址添加重定向。每次评估也会重查全站站内链接，因此修改或删除文章会暴露旧文中的失效引用。

评估报告中的错误要修复；编辑提示要结合上下文判断，合理的长段落或引用列表可以保留。涉及事实、API 行为或时间敏感结论的修改，仍要重新核对原始资料、适用条件和日期。评估通过并不等于事实核验完成。站外引用的可访问性由作者在修订相关内容时按需人工核对，不纳入自动巡检。

如果一篇文章的核心结论容易被误读，或已经因事实、适用边界、来源更新而修订过，应在 `evals/claims.json` 中为对应小节建立论断案例。案例记录结论、边界与原始来源；小节变化时重新阅读这些资料后再更新摘要。案例数量不是质量分数，来源存在也不代表论断自动成立。
