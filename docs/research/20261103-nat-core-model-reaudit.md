# NAT/P2P 文章核心模型再复核

日期：2026-11-03。对象：`content/zh/posts/20261102-nat-traversal-p2p-tailscale.md`（本次复核开始时的版本）。本记录不修改博客或 `claims.json`，也不构成实机 NAT 兼容性测试。

## 核心结论

没有依据认定现文中的“保持映射的 UDP 打洞三步例子”本身错误。它明确限定了两个重要条件：发往服务器和对端时复用外部映射，双方过滤需要此前联系过对应 IP 和端口。在这些条件下，首包可能被丢、双方主动发送后重试成功，与规范示例一致。

真正需要修正的是**总括解释的范围和缺失的层次**：开头和结尾把“能否访问另一台电脑”主要归因于 NAT 记录，未先明确接收地址、网络路径、独立放行策略和应用接收条件。读者容易因此把路由器、NAT、防火墙混为一谈，或以为拿到映射就等于访问到服务。

适合贯穿全文的模型是：**对方使用哪个可达地址接收数据；数据经过地址转换后交给谁；沿途是否允许该来源通过；目标程序是否准备接收。** NAT 穿透重点处理前几项中的地址与路径问题，不替应用自动启用服务、获得权限或提供安全认证。

## 必须收紧的表述

### 1. 用“知道响应交给谁”解释全部差异

原句：

> 区别在于：访问网站是内网设备先向外发出请求，路由器知道响应该交给谁；外部设备主动发来的数据，则未必有相应的转发关系和放行记录。

**判定：过宽且因果不完整，不是每个字都错误。** 已有 NAT 记录确实使反向转换成为可能；但一般“电脑互联失败”还可能是目标程序没有接收、独立入站策略不允许、没有路由等。不能把这些问题归为同一份路由器记录。即使全局可路由的 IPv6 没有 NAT，也可以执行有状态过滤。

建议直接替换：

> 能访问网站，只说明电脑可以主动与外部服务器通信。另一台设备要主动联系它，还需要一个能够到达的接收地址、允许这次通信的网络规则，以及正在接收数据的目标程序。设备位于 NAT 后面时，还要解决外部地址怎样对应到内部程序的问题。

依据：[RFC 3022 §2.2、§3.1、§4.1](https://www.rfc-editor.org/rfc/rfc3022.html)区分地址/端口绑定与反向转换；[RFC 6092 §3.2.3](https://www.rfc-editor.org/rfc/rfc6092.html#section-3.2.3)展示无须 IPv4 NAT 的有状态过滤；[udp(7) DESCRIPTION](https://man7.org/linux/man-pages/man7/udp.7.html)与[listen(2) DESCRIPTION/NOTES](https://man7.org/linux/man-pages/man2/listen.2.html)说明应用接收仍依赖对应 Socket 操作。

### 2. 把所有访问网站的路由器都写成 NAT

原句：

> 电脑访问网站时，数据会先经过路由器。路由器把内部来源转换成外部能够使用的地址，网站的响应也先回到路由器。这类地址转换机制通常称为 NAT。

**判定：示例中可以成立，作为无范围的一般陈述过宽。** 路由与 NAT 是不同功能；具有可路由地址的通信可以经过路由器而不发生地址转换。文章已经假设一个私网 IPv4 家庭拓扑，稍作明确即可，无须加入长篇例外。

建议：

> 在这个共享公网 IPv4 地址的家庭网络中，路由器除了转发数据，还执行 NAT：把电脑发出数据包的私有源地址改成外部可用的地址。返回数据经过相反的转换，再送回内部电脑。

依据：[RFC 3022 §1、§2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2.2)的 NAPT 拓扑和转换实例。建议称“在这个网络中”即可，不必引入新分类。

### 3. 只给转发目标，遗漏应用接收和独立策略

原句：

> 这就是端口转发。外部设备访问 `203.0.113.10:60000`，路由器就知道该把数据交给哪台设备的哪个端口。

**判定：句子本身是准确的教学表达，作为该方法全部条件不充分。** 端口转发定义目标转换；设备可能自动同时配置相关防火墙，但两者不能概念上视为必然同一操作。目标程序还要准备接收。

建议追加自然的一句：

> 这条配置确定了数据应转到哪里。目标程序仍需在对应端口接收，路由器和主机的防火墙也必须允许该流量。

依据：[RFC 3022 §2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2.2)的静态端口映射；[RFC 4787 §4.1、§5](https://www.rfc-editor.org/rfc/rfc4787.html)分别定义映射与来源过滤。应用接收见前述 Linux 手册。不要反过来断言所有设备上做端口转发后必定还要手动单独设置防火墙。

### 4. “双方都主动发送”被概括成全部入站通信的必需条件

原句：

> 路由器会记住内部程序向谁发过包，两台电脑都主动向对方发送，就有机会让对方的返回包通过。

**判定：典型目的相关过滤下成立，普遍化过宽。** 有些过滤规则在映射建立后不限制远端来源；某一方直接可达时，还可以反向发起连接。双方对发是要解释的常见打洞机制，不是所有通信都必须执行的前置步骤。

建议：

> 当两边都限制外部主动来包时，可以让程序交换候选地址，再各自向对方发包。对要求内部先联系过该来源的网关，这些出站包有机会形成允许后续来包的状态。能否成功，还要看地址映射是否可用。

初学版可更短，但保留“当……”“有机会”及映射条件。

依据：[RFC 4787 §5](https://www.rfc-editor.org/rfc/rfc4787.html#section-5)中 EIF 不要求先向特定来源发送；[RFC 5128 §3.2、§3.3](https://www.rfc-editor.org/rfc/rfc5128.html#section-3.2)分别讨论单边可达时的连接反转与双边 NAT 打洞。

### 5. UDP 的应答语义

原句：

> 每份数据作为独立的数据报处理，是否收到需要程序通过应答判断。

**判定：容易让读者误以为 UDP 要求逐包应答；应收紧，不能称它为协议规定。** UDP 不提供交付确认，但应用可以不关心某个数据报的交付。打洞应用若要确认双向路径，则会自定义检查事务或应答。

建议：

> UDP 不会自动确认数据是否送达。打洞程序为了判断路径能否双向通信，会自行发送探测消息并检查应答。

依据：[RFC 768 Introduction](https://www.rfc-editor.org/rfc/rfc768.html)说明交付与去重不保证；[RFC 5128 §3.3.1](https://www.rfc-editor.org/rfc/rfc5128.html#section-3.3.1)讨论双方交换消息以建立 P2P 路径。这里不应泛化为所有业务都必须逐包 ACK。

### 6. 结尾将 NAT 场景推广到一切出站响应

原句：

> 内网设备发出的请求能够收到响应，是因为网关保存了地址转换和通信状态。

**判定：范围错误。** 有状态 NAPT 场景需要该状态，但不是所有网络都有地址转换，更不是响应存在的唯一原因。

建议替换为：

> 在使用动态 NAT 的网络中，出站流量建立的映射让返回数据能够被转换回内部地址；能否通过则还受过滤策略影响。P2P 直连需要找到双方实际可用的接收地址，并验证整条路径。

依据：[RFC 3022 §2.2、§3.1](https://www.rfc-editor.org/rfc/rfc3022.html)、[RFC 4787 §5](https://www.rfc-editor.org/rfc/rfc4787.html#section-5)。

## 不应为了迎合批评而误判的内容

### 7. “家用路由器会保存转换关系”

**判定：给定有状态 NAPT 示例中的准确基础说明。** “路由器记住”是合理比喻，不是认知错误；改成十几个内部表项术语反而损害教学。应补足应用与过滤条件，不应删除转换模型。

### 8. 第一包被丢、B 出站、A 重试的时序

**判定：在已写出的映射复用和精确过滤前提下准确。** 既不要求严格同时，也没有把 NAT 写成判断负载中谁回复谁。无需推翻，应让“两份状态分别由各自出站包建立”的因果更突出。

依据：[RFC 5128 §3.3.1](https://www.rfc-editor.org/rfc/rfc5128.html#section-3.3.1)；[RFC 4787 §5](https://www.rfc-editor.org/rfc/rfc4787.html#section-5)。

### 9. 私有 IPv4 地址不能在公网直接投递

**判定：原文按普通公网路由语境表达，准确。** 通过 VPN 或私有互联可达不推翻这个结论；不要为了防例外而在开头引入覆盖网络和地址域。

依据：[RFC 1918 §3](https://www.rfc-editor.org/rfc/rfc1918.html#section-3)的私有地址作用域与跨企业路由限制。

### 10. “P2P 通信系统中服务器可协调或中继”

**判定：方向准确，原文没有明确写成 P2P 等同于直连。** 需要注意其中“确实无法直连时，再由中继”只能是常见策略，不能写成强制时序。后面的 Tailscale 章节已经正确说明中继与直接探测可并行。

建议：

> P2P 系统可以借助服务器发现对方、交换地址，也可以让服务器提供中继路径。业务是否直连、何时切换，由实际可达性和连接策略决定。

依据：[RFC 5128 §3.1–3.3](https://www.rfc-editor.org/rfc/rfc5128.html#section-3.1)将中继、连接反转和打洞都列入 P2P 穿透技术。

## 其他部分的抽查

- 已见的 EIM/ADM/APDM 与 EIF/ADF/APDF 定义、CGNAT 非固定行为类型、IPv6 仍有过滤、基础 TURN 的客户端传输与服务端 UDP 两段、TCP 同时打开序列，都未见本次需要推翻的实质错误。
- Tailscale 章节正确保留未知路径时 DERP 与直接探测可配合进行、Peer Relay 需要 UDP 可达、默认 DISCO 不等于应用服务验证、41641 受部署配置影响等限制；本次没有重新断言所有产品版本完全一致。
- 性能部分区分 Socket、内层流和外层五元组，没有从端口数量直接推出并发与带宽；没有发现需要借本轮整改推翻的结论。
- “WireGuard 加密与重放保护”并不替代内层业务可靠传输，现文已有这个区分。

## 建议的核心开头

可保持浅显，同时把问题聚焦在网络可达性：

> 两台设备要直接通信，一方必须知道对方当前可用的接收地址，数据能够沿网络送达，并且对方的程序愿意接收。设备位于不同内网时，内部 IP 通常不能直接作为公网目的地址；网关又可能限制外部主动来包。
>
> NAT 穿透要解决的是这条路径如何建立。UDP 打洞先借助公网服务发现可尝试的外部地址，再通过端点之间的探测，让允许这类通信的 NAT 和防火墙形成可用状态。直接路径不可用时，可以改用中继。
