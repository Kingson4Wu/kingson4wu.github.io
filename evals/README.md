# 博客内容评估

发布检查分成几层。`npm run check` 检查全站基础内容和本地图片；`npm run eval` 离线检查全站文章的站内链接与关键论断，同时只对本次新增或修改的文章给出编辑提示；`npm run build && npm run check:site` 检查生成后的每个页面、站内链接、锚点和本地资源。浏览器冒烟检查覆盖中英文首页、搜索页、最近的文章和笔记，以及本次改动的旧文；在手机和桌面宽度下检查渲染，并操作搜索、文章目录和主题切换。

```bash
# 查看全部现有文章的评估结果
npm run eval -- --all

# 模拟改动一篇文章：全站链接照常检查，编辑反馈集中在这篇文章
npm run eval -- --changed-only --changed-file content/zh/posts/example.md

# 新文章使用更严格的元数据检查
npm run eval -- --changed-only --new-file content/zh/posts/example.md --report /tmp/blog-eval.json

# 构建产物和浏览器检查
npm run build
npm run check:site
npm run check:browser

# 检查本次改动的旧文；参数可以重复
npm run check:browser -- --changed-file content/zh/posts/example.md
```

CI 根据 Git 改动自动传入 `--changed-file` 或 `--new-file`，并通过 `--base-ref` 比较旧文的公开地址；如果修改了旧文 slug，需要保留原地址或在 `content/legacy-redirects.json` 中加入指向新地址的重定向。历史文章的 slug 可以与文件名不同；语言和类型始终要与目录一致。即使没有文章改动，文章链接仍会全站检查，这样删除文章或改变路由时，旧文中的失效引用也会被发现。报告包含文件、行号、规则和理由；CI 还会把这些诊断显示为源文件行号上的注释。`error` 阻止部署，`warning` 只供复核。PR 与主分支均执行评估，只有主分支通过全部检查后部署。

`claims.json` 中每个案例绑定一篇文章的路径、小节、原文短句、来源 URL、来源中的具体核查位置、核查日期和该小节的 SHA-256 摘要。每个来源 URL 都需要一个对应的 `sourceLocators` 条目。优先记录影响结论的论断、数字和容易被误读的边界，不按文章数量凑覆盖率。服务商能力、研究预览状态等会变化的论断可设置 `reviewBy`；到期后评估会给出复核提示。修改小节后，先核对原文、适用条件和引用资料，再更新摘要与核查记录。摘要失配只表示原文变化；摘要相同也不能证明论断真实。不要机械刷新摘要或填写并未完成的人工审阅记录。

编辑提示刻意保持少量、可解释：明显的写作过程旁白、过长的可见正文段落、连续堆列的链接。它不会自动改写文章，也不会以统一句式或篇幅评价个人表达。站外链接可达性、事实准确性和论证质量仍需作者或审稿人判断。

浏览器检查在基本渲染和交互之外，还检查正文最小字号、标题和图表的水平边界；CI 保存手机和桌面的页面截图供人工查看。主分支通过全部本地检查后，工作流为固定代表页面、本次修改的文章和样式文件记录内容哈希，上传同一份 `dist` 作为 Pages 产物。部署任务直接发布该产物，并核对线上文件与已验证构建的哈希。这样既能发现无法访问的页面，也能发现发布后仍读到旧内容。
